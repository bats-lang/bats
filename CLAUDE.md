# bats

## Goals

bats must be:

1. **The bats compiler**: Self-hosting bats compiler written in Bats. The old Rust implementation is archived at `/home/moshez/src/bats-lang/bats-old/`.

2. **Safe**: `unsafe = false` (or no `unsafe` key) in `bats.toml`. No `$UNSAFE begin...end` blocks in bats source. No `$extfcall` — it is an unsafe construct. C code belongs in library packages (file, process, sha256, etc.) that expose safe typed APIs. If a package must be `unsafe = true`, keep the unsafety minimal — expose safe wrappers so dependents can be `unsafe = false`. Being in an unsafe package is not carte blanche to add more unsafety.

## Bootstrap seed

`bootstrap/c/` is the checked-in C output of the compiler (`bats build --to-c`), normalized by `scripts/bootstrap-c.sh` so it is byte-identical on every machine. It is the only thing needed to get a working `bats` from scratch:

```bash
cp -R bootstrap/c /tmp/seed && make -C /tmp/seed debug/bats
```

Every change to `src/` or `bats.lock` must regenerate and commit it in the same PR:

```bash
dist/debug/bats build --repository ../repository-prototype
scripts/bootstrap-c.sh dist/debug/bats ../repository-prototype
```

CI builds the compiler from `bootstrap/c`, regenerates, and fails if the result differs. It also checks the fixpoint (the compiler built by itself emits the same C). Never edit `bootstrap/c/` by hand.

## Architecture

Entry point: `src/bin/bats.bats`
Shared modules: `src/helpers.bats`, `src/lexer.bats`, `src/emitter.bats`, `src/build.bats`, `src/docs.bats`, `src/commands.bats`, `src/lock.bats`, `src/recursion.bats`, `src/closure.bats`, `src/cache.bats`, `src/facts.bats`, `src/inputs.bats`

Dependencies: argparse, array, arith, builder, env, file, path, process, result, sha256, str, toml

## Workflow

All changes, even one byte, in ANY repo in bats-lang, must go through branch -> PR -> green -> merge. NEVER commit directly to main. Use `gh pr merge --merge` (no squash).

When creating a new repo: push an empty initial commit to main first (`git commit --allow-empty -m "Initial commit" && git push -u origin main`), then create a feature branch for the actual content. The first branch you push becomes the default, so main must exist before any feature branches.

Never blocked by another PR — add finishing that PR to the task list instead.

Never ask permission to keep going. Keep going until the success criterion is met.

Never wait. A PR in flight (CI running, a package publishing, a review pending) is never a reason to stop or idle: pick up the next independent task from the task list (this project always has one) and come back to the PR when its event arrives. Stopping is only for a decision that is the user's to make.

## Allowed Divergences from old Rust bats

bats uses `--only <value>` (repeatable) instead of the old Rust bats' `--release` flag and `--only native|wasm`. Values: `debug`, `release`, `native`, `wasm`. Multiple `--only` flags narrow the build matrix. Default (no `--only`): build all. Example: `--only debug --only native` builds only debug native. The entry point rename (`implement main0` → `implement __BATS_main0`) applies to code only. The Rust bats renamed the first occurrence anywhere in the emitted text, including inside a string literal or a comment, which broke the build (`tests/main0-string`).

`castfn`, `praxi`, `extern` and `assume` at the start of a `#pub` declaration are rejected as unsafe constructs; the Rust bats let a `#pub` declaration through unchecked (`tests/restricted-keywords`).

The `end` that closes `$UNSAFE begin` is found in code only; the word `end` in the C of a `%{ ... %}` block (a comment, say) does not close it. The Rust bats closed the block there, which broke the build (`tests/unsafe-extcode-end`).

`$X.member` is accepted when `X` is bound by ATS's `staload X = "..."` as well as by `#use ... as X`; packages staload bridge modules this way. The Rust bats reported "unknown alias" for a staload alias (`tests/staload-alias`).

A dependency's `#pub` names are not renamed. The Rust bats renamed each dependency file's `#pub` names to `__BATS__<pkg>_<name>` on its own, so a call from one module of a dependency to another module's `#pub` function (as in bridge) no longer resolved (`tests/dep-cross-module`).

The wasm prelude defines `atspre_cloptr_free` (as ATS's `basics.cats` does, with `ATS_MFREE`). The Rust bats's wasm prelude lacked it, so a wasm binary that freed a closure imported it from a host that has none and failed to instantiate (`tests/wasm-cloptr-free`).

The wasm prelude defines `atspre_g0int_nmod_int`, `atspre_g1int_nmod_int`, `atspre_g1int_mod_int` and `atspre_neg_bool0`/`atspre_neg_bool1` (as ATS's `integer.cats` and `bool.cats` do). The Rust bats's wasm prelude lacked them, so `nmod` and `~b` in a wasm binary were imported from the host, which stubbed them to return 0 (`tests/wasm-prelude-arith`).

The wasm prelude defines `atspre_ptr_is_null`, `atspre_ptr_isnot_null` and their `ptr0`/`ptr1` forms (as ATS's pointer.cats does). The Rust bats's wasm prelude had only `atspre_ptr_isnot_null` and `atspre_ptr0_isnot_null`, so a wasm binary that made an arena (array's `arena_create` tests its region with `ptr1_isnot_null`) imported the rest from a host that has none and failed to instantiate (`tests/wasm-prelude-ptr`).

The wasm prelude defines ATS's literal pattern checks `ATSCKpat_int`, `ATSCKpat_bool`, `ATSCKpat_char` and `ATSCKpat_float` (as `pats_ccomp_instrset.h` does), which patsopt emits for a `case` on a literal. The Rust bats's wasm prelude had only `ATSCKpat_con0` and `ATSCKpat_con1`, so a wasm binary with such a `case` (css's unit table) imported `ATSCKpat_int` from a host that has none and failed to instantiate (`tests/wasm-prelude-patterns`).

The wasm prelude's `ATSCKpat_con1` checks that the value is a pointer (at least `ATS_DATACONMAX`, 1024) before it reads the constructor tag, as ATS's `pats_ccomp_instrset.h` does. The Rust bats's did not, so in a wasm binary a nullary constructor (a small integer) matched against a constructor with fields was read as an address: with its tag read as 0 it was taken for the first constructor, whose fields were then read and freed (`tests/wasm-prelude-con1`).

The wasm prelude defines the `uint` operations (`atspre_g0int2uint_int_uint`, `atspre_g0uint2int_uint_int`, `atspre_g0uint_add_uint` and the other arithmetic, comparison and bit operations, their `g1uint` forms) and the char comparisons (`atspre_eq_char0_char0`, `atspre_neq_char1_char1`, ...), as ATS's `integer.cats` and `char.cats` do. The Rust bats's wasm prelude lacked them, so a wasm binary that hashed with sha256 or compared chars imported them from a host that has none and failed to instantiate (`tests/wasm-prelude-uint`).

A wasm binary exports `bats_dynload`, the entry's dynload (named with ATS's `ATS_DYNLOADNAME`), which the host calls before `mainats_0_void`. The Rust bats's wasm had no way to run the dynloads, which a native binary's C `main` runs, so no module `val` was ever initialized: a module's `ref<int>(42)` was a null pointer, and reading it read address 0 (`tests/wasm-dynload`). The wasm prelude also defines `atspre_ptr_alloc_tsz`, with which `ref` allocates its cell, as ATS's pointer.cats does.

Every recursion needs a termination metric outside `$UNSAFE`, as a `fun` does: `fnx`, the `and` members of a `fun` or `fnx` group, and `fix` lambdas are rejected without `.< metric >.`, and `val rec` (which cannot carry one) is rejected. The Rust bats checked only the `fun` keyword, so these recursed with no termination proof (`tests/recursion-metrics`).

A `$UNITTEST` block is lexed as code, like a `#target` block (a begin span, its contents' spans, an end span), so an unsafe construct in it is rejected as anywhere else; the Rust bats copied a block's text verbatim, unchecked. A block closes at its own `end`, not at the first `end` inside it (a `let`'s), where the Rust bats closed it. A `#target` block inside a `#target` block keeps its code; it was dropped (`tests/unittest-blocks`).

`bats test` runs the tests. The Rust bats's runner called each test from a generated entry that staloads only the modules' `.sats`, where a test (defined in its block, in the `.dats`) is not declared, so it could never compile. In check and test mode each module with tests now declares `__bats_test (i: int): bool` in its `.sats` and implements it in its `.dats`, dispatching to its i-th test; `bats test` builds a runner binary in `build/_bats_test` (the package's `src/*.bats` and one binary whose `main0` calls the selected tests) and runs it, with the Rust bats's `running N native test(s)`, `  PASS <name>`/`  FAIL <name>`, `error: native test failed` and `all tests passed`. A test is `fn <name> (): bool` in a `$UNITTEST.run` block (a test `fun` would need a metric); tests in `src/bin/` are an error (the runner links `src/`'s modules, not the binaries) (`tests/test-command`). Wasm tests run the same way: a `#target wasm binary` runner in `build/_bats_test_wasm`, run in Node by a generated harness, printing the Rust bats's `running N wasm test(s)`, the PASS/FAIL lines, `P passed, F failed` and `error: wasm test failed`. For it the wasm runtime defines `print_string`, `print_newline`, `print_int` and `exit_void` over the host imports `env.bats_host_print` and `env.bats_host_exit`, which the harness provides; the Rust bats's harness called exported test functions instead, which a `.sats`-less test could not be (`tests/test-wasm`).

An `implement` on a call cycle is rejected: one that calls itself, directly or through other implements or top-level functions, in the package or in a dependency. A metric cannot be given to a function declared in a `.sats`, so ATS never checks an implement's recursion for termination; the Rust bats let it through. The calls are read from the sources (`src/recursion.bats`): a definition calls every definition its body names unqualified, an implement's name being visible in every file and another definition's only in its own, and the calls within a `fun` group, which its metric checks, are left out (`tests/implement-recursion`).

With a `bats.lock`, `check`, `build`, `run` and `test` use exactly the versions it locks, transitive ones too (`locked_deps` in `src/lock.bats`). The Rust bats's `resolve_deps`, and this one until now, never read the lock: they fetched the newest version of each package `src/` uses directly, so a committed lock pinned nothing and a missing locked version went unnoticed. Now each locked package that `bats_modules` does not hold at its locked version (the `.bats-version` stamp `fetch` writes, or the package's `bats.toml` version) is fetched from the repository after its archive's sha256 is checked against the lock, replacing what was there; a locked version the repository lacks, an archive of another sha256, or no `--repository` to fetch from is an error. A lock that does not match the project is an error too, with a hint to relock: a package used but not locked, one locked but not used, or a locked version `bats.toml`'s constraints rule out. Newer versions in the repository are not an error; `bats lock --dry-run` still reports them as a stale lock. `bats lock` replaces what `bats_modules` holds of another version, so a relock reads each package's own `#use`s from the version it locks (`tests/locked-deps`). Without a lock, the newest version of each package `src/` uses is fetched, as before.

A build reuses what an earlier build produced when it is still fresh; the Rust bats rewrote every `.sats` and `.dats` on every build, so its cache (input mtime equal to the recorded one) reran patsopt on everything. A `.bats` is emitted again only when its bytes are not those its `.dats` was emitted from (their sha256, kept in `<dats>.src`; an mtime cannot tell, since a relocked dependency's files keep their archive's older mtimes, `tests/source-replaced`); its `.sats` is written only when its bytes change, and then `build/.sats_changed` is written. Nothing reads a time to decide what is fresh (bats#254: a build and its inputs are made in one whole second, a stash is moved with its mtimes, a file is touched or replaced with an old time; each gave a build that did the work again, or not at all). A module's C and its object each have a key beside them, `<C>.key` and `<object>.key`, written after the tool passed and removed before it runs: for a C the size and the sha256 of its `.dats` and of `build/.sats_changed`, for an object those of its C (the flags, the target and the mode are in `build/.bats_stamp`, which drops a `build/` that differs). An output is fresh when it is there and its key equals the one its inputs give now; the sizes are compared first, and a different size is a changed file with nothing hashed. A key that is missing, short or garbled makes its output again. `build/.sats_changed` is written whenever an emitted `.sats` changes, with new bytes each time (the sha256 of what it held), so in a build a change to a `.sats` rebuilds every module's C, as before (in check and test mode the keys name the files each module read instead: below), and a body-only change rebuilds only its own module (`tests/sats-change`). The same keys serve the dependencies under a namespace (bridge, dom), the extra modules of a dependency, the wasm objects, the binary's own module and the entry's object (the entry's C is made again by every build, and an object is made again only when that C differs). The cost: every no-change check reads and hashes each module's `.dats` and each C once; the tests are `tests/build-content-keys`, which plays the no-change runs after a cold one with no settling, every file of `build/` given a time in the future and long ago, a changed body of the same size, a changed `.sats`, and a garbled or missing key.

In check and test mode a module is not checked again when the files patsopt read for it are unchanged (bats#267, item 3; `src/cache.bats`, `tests/check-memo`). The record is the same `<C>.key` beside the C, in a text of its own: `bats-memo 1`, a `names` line (the sha256 of the sorted names of every `.sats` and `.hats` under `build/`, the stashes of other marks left out), the module's closure (one path a line, the list `patsopt --depgen` gives followed to the end, which is the `.dats`, every `.sats` and `.hats` its staloads and includes reach, and a staloaded dependency's `.dats`), a `--` line, the size of each of those files in order and of `build/.bats_stamp`, and then their sha256s in order and the stamp's. The list is the key's own, read back from it, so `patsopt --depgen` runs only when patsopt ran and passed (bats#253 measured 0.4 s a module), and a later check only rehashes the files named. The first module of a pass that needs a list fills a graph (`build/.bats_graph`, a line `<file> <TAB> <the files it names>`) with one `--depgen` of every `.dats` and `.sats` of `build/src` and `build/bats_modules`, and the walk to the end is done on that graph, so a file that many modules reach is read by patsopt once; a file the graph lacks is asked for, a level at a time, and added. The graph is removed whenever the names are listed again (below), so it is never older than the files it was made from; its answers were compared with the level-by-level walk's on each module of bats's own project (same list for every one). It is written after patsopt and `check_emitted_flaws` passed, to `<C>.key.new` and renamed into place, so a reader sees a whole key or none, and removed before patsopt runs (a failed or killed run leaves none; a module that failed is never recorded and is checked again at the next run, whatever its bytes). Fresh means the C is there and the text made again from the files as they are now begins with, and then equals, the key's: the sizes are compared first, then the hashes. A key that is missing, short, garbled, of another format or with one number changed is not equal, so the module is checked. No time is read anywhere in it. `bats check --cold`, or `BATS_COLD` set to anything but `0`, ignores every key and writes them again (main's run is meant to use it, as quire's does for `build/`). `-v` prints `  = <C> (unchanged)` for a module skipped. The stamp is not repeated in the key's rule: `build/.bats_stamp` is judged first and drops a `build/` that differs, and its size and sha256 are the key's last line of each part, so the toolchain, the compiler, the flags and this bats are in the key through it. Build mode is unchanged: its keys still name `build/.sats_changed`, so a changed `.sats` rebuilds every C there, since a C that is shipped is not to be trusted to a closure bats cannot prove complete.

Three things are not obvious. (1) A `.sats` is digested as its interface, not its bytes: its length and sha256 are those of its text with each run of line feeds taken as one, tagged `C`, so a declaration added before a module's `#pub` ones (a static fixture's snippet) moves the `.sats` and changes no module that staloads it, as `sats_moved` has it for the `.sats_changed` stamp; a `.sats` with a line feed in a string or char literal, a `%{` or an open comment is digested as it is, tagged `R`, the same lexical scan `sats_moved` uses (`newlines_between_tokens`). The "size" of a `.sats` is the length of that text, so it is still a negative only. (2) A module's closure is what patsopt reads, so a body-only change to a staloaded dependency's `.dats` checks the modules that staload that `.dats` again (a bin that `#use`s a dependency does), which the `.sats_changed` stamp did not and which is right: patsopt reads a staloaded `.dats` (templates). (3) A file that patsopt would have read had it existed, a `.sats` of the same name earlier on `-IATS build -IATS build/src -IATS build/bats_modules`, is in no module's list, so the `names` line holds the name of every `.sats` and `.hats` of `build/`: a module added or removed (or a dependency, whose `.sats` appear in `build/bats_modules`) checks every module again. That is conservative on purpose. The digests of the files many modules share are kept for a run too: a `.sats` and every file under `build/bats_modules` (a staloaded dependency's `.dats` is several hundred kilobytes, and its sha256 in a debug bats is slow) are digested once, into `build/.bats_dg/<path with / as %>` (the path, a line feed, the size line, the hash line), and read from there by the other modules; a module's own `.dats` is hashed where it is needed. The directory is emptied with the graph whenever the names are listed again, so an entry never outlives a run or the files it digests. The listing (`build/.bats_names`) is made once after anything that adds, removes or moves such a file (`names_set_fresh(false)`: a `.sats` emitted, which is `touch_sats_stamp`, `build/` swapped in by `cache_swap`, the orphans pruned) and its sha256 is read at each lookup; before this it was a `find` and a sort for each module, twice, which made a no-change check 9 to 12 s slower than main's.

What is not proved, and is checked another way: that `patsopt --depgen` lists every file a module's check reads (it is the walk `BATS_CACHE_DIR`'s key has used since bats#250; its limits are patsopt's, and a `staload` of a file by a name built from the environment is not seen); that the squeezed text means what the original does (the lexical scan is a function of the bytes and is tested, `tests/sats-moved`, not proved); that renaming into place is atomic on the file system in use (POSIX says it is on one file system; a `build/` on a file system that is not is not covered); and that `names` is read before patsopt runs and the closure after, with nothing between them that changes a `.sats` (bats holds the project's lock, so only bats itself does, and all the emissions are done by then). `--cold` on main is the detector for a closure that missed a file, as it is for `build/` in quire. `patsopt --depgen` is started by `sh` in every case and is held to `BATS_PATSOPT_TIMEOUT_S` and `BATS_PATSOPT_MEM_MB` by the same wrapper `patsopt_only` uses (time: status 124, memory: 125, the same error naming the module; a depgen that hangs once hung a `check` past the cap); `tests/patsopt-cap` plays a hanging `--depgen` and leaves depgen out of its count of who started patsopt, since sh starts it whether a cap is set or not. A key that would reach 524288 bytes (the most bats writes) is not written, and `-v` says so; the module is then checked again at each run. The root package of a library (`build/src/lib.dats`) was checked at every `bats check` whatever its inputs; it is skipped now by the same key. Measured (one machine, 4 cores, one `bats -v check` at a time, main's bats at cb6ab0e against this one; seconds and patsopt runs, then `--depgen` starts for this one) on bats's own project of 33 modules and on a project of six modules and two bins, a native and a wasm one, over arith, array, builder, css, str, widget, promise, result, json, bridge and dom. Own project: cold 84 s, 33 runs against 89 s, 33, 2 starts; no change 35.3 s against 37.6 s; a leaf module's body changed 36.7 s, 2 runs against 39.3 s, 2, 1 start; a leaf module's `.sats` changed 81.9 s, 33 runs against 42.3 s, 4, 2 starts. The other project: cold 126 s, 110 runs against 141 s, 110, 4 starts; no change 33.4 s against 39.5 s; body 34.2 s, 2 against 41.8 s, 2, 2 starts; `.sats` 143.5 s, 110 against 42.8 s, 4, 3 starts. The first version of this memo started `--depgen` 86 times on a cold check of the own project and 300 on the other (one patsopt per level of each module's closure) and took 104 s and 183 s. The memo is not at parity where nothing changed or only a body did: 2 s (own project) and 6 s (the other) slower, which is the digest of the files a module's closure holds that main never read, taken once for a pass: a staloaded dependency's `.dats` (bridge's and dom's are the large ones) and the `.sats`, whose sha256 in a debug bats runs at a few hundred kilobytes a second (stack samples of the no-change check are mostly the sha256 rounds), against main's one `.dats` for each module. Hashing less would mean trusting a `.dats.src` sidecar for a file bats wrote (a kill between the two writes leaves a `.src` that is not the `.dats`'s), which is not done; a release bats would be faster. The roughly 20 s that bats spends before its first child process in every check (bats#296) is the same in both and is not touched. The neighbouring tests changed with this: `tests/build-content-keys` no longer expects a changed `.sats` or a stamp ahead to check every module (a check does not read `.sats_changed`; the build part of the test does), and expects a changed body of a dependency to check the bins that staload its `.dats`.

A string literal whose last byte is an escaping backslash is an unterminated string, reported as the Rust bats reports any other ("unterminated string literal"); the Rust bats's lexer stepped past the end of the file there and panicked (`tests/unterminated`).

What allocates must be linear outside `$UNSAFE`, since wasm has no garbage collector and a non-linear boxed value is never freed. Each of these is rejected, with a message that names the linear form to use: a `datatype` with a constructor that carries data (use `datavtype`; `of ()` is nullary); a boxed tuple, record or list (`'(`, `'{`, `'[`, `$tup`, `$rec`, `$list` and their `_t` forms; use `@( )`, `@{ }`, `$tup_vt`, `$rec_vt`, `$list_vt`); a non-linear closure (`cloref`, `cloref0`, `cloref1`, `cloptr`, `cloptr0`, `cloptr1`; use `lincloptr1`, made with `llam`); a `lam` whose arrow leaves its kind to its context (given to a cloref parameter, the prelude's included, it is a `cloref1` closure; use `llam`, or the arrow `=<fun1>` for a plain function; `lam@` is a flat closure and stays); and a `ref` made inside a function (`ref<...>(` or `ref_make_elt` on an indented line; a top-level one is made once and stays). So are the prelude's own non-linear builders, which the source names without writing a `datatype`: the constructors of `list`, `option` and `stream_con` (`list_cons`, `list_nil`, `Some`, `None`, `stream_cons`, `stream_nil`) and the macros `nil`, `cons` and `::` (unless the file declares its own `nil` or `cons`, as the list package does over `list_vt`); every prelude function whose result is a non-linear list, option or stream built from something that is not one (enumerated from the prelude's SATS files: `list_append`, `list_vt2t`, `option_of_option_vt`, `stream_make_nil`, ...); `$delay`; and libats/ML, ATS's garbage-collected library (its `list0`, `Some0`, ..., and any staload or include of it). A qualified name (`$R.some`) is another package's and stays; the messages name `list_vt`, `option_vt` or result's `option`, and `stream_vt` (`tests/prelude-builders`). The Rust bats let them all through (`tests/linear-heap`).

A template instance patsopt finds no implementation for (`PMVtmpltcstmat` in the C it emits) fails `bats check` and `bats build` right after patsopt, with an error that names the template, shows the instance, and points to the `.bats` line that uses it. The Rust bats's check passed it, since check runs no cc, and only cc rejected it at build, with an error in the generated C (`tests/template-instances`). So does a lambda whose kind is a plain function but which captures a variable (`ATSERRORnotenvless` in the C), pointing to its `.bats` line (`tests/capturing-function`).

patsopt's C names the project's files relative to the project (`build/src/m.dats`): after patsopt succeeds, `src/cache.bats` takes the project's directory out of the paths it wrote, plain in comments and mangled into symbol names, where it is followed by `build/` (`build_057_`), as GCC's `-ffile-prefix-map` or Rust's `--remap-path-prefix` do. The same sources give the same C at any path, so a `build/` and the shared cache below are valid wherever the checkout is; ATS's `$mylocation` names its file relative to the project. The Rust bats's C held the absolute path, so a `build/` was valid only where it was made. patsopt writes `<C>.raw`, which is rewritten beside the C and renamed into place, so a bats stopped at any point never leaves a C that is half written or still holds the path (`tests/project-lock`, `tests/shared-cache`).

With `BATS_CACHE_DIR` set, patsopt's C is kept there, under a key of what patsopt reads: the toolchain (a listing of `$PATSHOME/bin/patsopt` and the files of `prelude/`, `libats/`, `share/`, `ccomp/` by `cksum`, made once per process), patsopt's arguments, and the module's `.dats` with every file its staloads and includes reach (`patsopt --depgen`, followed to the end), each by path and sha256. A module bats would run patsopt on is looked up first; a hit is copied into place and checked as patsopt's output is (template instances, capturing lambdas), and only a run that passed those checks is kept, so a hit never passes what a cold build fails. Entries are written beside their place and renamed into it, so checkouts share the cache with no lock; one unused for 7 days is removed (at most once a day, after a store). The Rust bats had no cache shared between checkouts (`tests/shared-cache`).

`bats ats2 install` installs the ATS2 bats runs (patsopt, the GMP build) into `$HOME/.bats/ats2`; `bats clone-repository <commit> --repository <dir>` clones the package repository at a full commit; `bats record-commit <commit>` checks a commit is in the repository of the working directory. They are the three steps of the setup action (`.github/actions/setup`) after bats is built from `bootstrap/c`, as subcommands and not scripts, on the owner's ruling (bats#283); the command word must match exactly, and a further argument, a word after `--` and an unknown option are usage errors (exit 1). `ats2 install` takes no options: the pin (`ATS2-Postiats-gmp-0.4.2`, its https URL, its SHA-256) is the three constants of `src/ats2.bats` and nowhere else (`scripts/check-pins.sh` fails a workflow or action that names a tarball or a digest, or a pin that is not a SHA-256 and an https tarball). It downloads with `curl` (connect timeout 20 s, 900 s in all, 3 retries) into a directory of its own made by `mktemp -d` (bats runs curl, tar, make and git through the process package; no package of the repository is an HTTP client, and TLS is not reimplemented here), checks the download with bats's own SHA-256 against the pin before unpacking, unpacks with `tar --no-same-owner` and builds patsopt in `~/.bats/ats2.new`, moves it into place whole and writes `~/.bats/ats2/.bats-ats2` (the pin's name and SHA-256) last. Two installs at once take turns: the file package's `fd_lock` on `~/.bats/ats2.lock` is held while ats2 is installed, and what is installed is judged again under it. A marker equal to the pin's with `bin/patsopt` there is already installed and nothing is done; a marker of another pin is replaced, and so is an empty directory; anything else at `~/.bats/ats2` that bats did not make (a directory with other files, a link to one) is refused with a message, before anything is downloaded, and left as it was (`rm -rf` is only ever run on bats's own marked toolchain and on its own temporary directories); `bin/patsopt` with no marker (a developer's own toolchain, or an `-int` build) is used as it is, never replaced, and **every process that runs build, check, test, run or ats2 install says so once on stderr** ("warning: the ATS2 in ... was not installed by bats and is not checked ..."): that toolchain may be an `-int` build, which accepts false statements, and telling one from the GMP build is bats#264's hazard, still open (the fixture tests that compare messages exactly want a toolchain bats installed, as CI has, or a marker written by hand for the same tarball; a developer's own toolchain makes them show this warning). What a killed run left (`ats2.new`, `ats2-download.*`, an old `ats2.tgz.part`) is cleared at the next install. `bats build`, `check`, `test` and `run` call the same function when `bin/patsopt` is missing (the old unverified curl install is gone). libgmp and its headers are the system's. The other two print `NAME=VALUE` (`BATS_REPOSITORY=<dir>`, `BATS_COMMIT=<commit>`) on stdout and everything else on stderr, so a CI step redirects stdout to its environment file (GITHUB_ENV's format) and bats knows no CI; a directory with a control character in its name is refused, since the line could not hold it. Both want a full commit (40 lowercase hex digits, never a branch or tag). `clone-repository` deletes nothing that this run did not make: a directory that is a git repository is used only when its `origin` is the pinned repository's URL (then fetched and checked out in place; a clone already at the commit is left alone), an absent or empty path gets a clone made in a sibling directory of the run's own (`<dir>.new.XXXXXX`, holding a `.bats-clone-pending` marker with the pid of its shell while it is made; the next run removes a marked sibling only when that pid is no longer alive, so a killed run's sibling goes and a sibling whose shell lives on (bats killed alone: the shell goes on to its clone, which it moves into place) is kept, never removed under a writer) and moved into place (`rmdir` of an empty target, which keeps its mode, setgid and sticky bits included, and is made again if the move fails, so a directory with anything in it can never be replaced), removed again by a trap on any failure and on INT and TERM, together with the parent directories the run made for it (none that were there before, so a failed `a/b/c` leaves `a` as it was), a symbolic link is refused, and every other path (any other directory, a git project of the user's, a file) is refused and left exactly as it was; a failed run leaves the directory as it was. The repository's URL is a constant in `src/setup.bats` and the tests redirect it with git's `url.<base>.insteadOf` in the environment. The setup action fails when the pinned bats commit predates this change (no `_bats_native_runtime.h` in its `bootstrap/c`) and lets only a single well-formed `NAME=VALUE` line reach `$GITHUB_ENV` (an old bats prints its usage and exits 0 for a command it does not know). Tests: `tests/ats2-install`, `tests/clone-repository`, `tests/record-commit`.

The C of `bootstrap/c` builds with no ATS2 installed (bats#283): `--to-c` writes `_bats_native_runtime.h`, a header for the ATS2 C runtime macros and prelude functions the generated C uses (the same text as the wasm build's, `put_runtime_macros` in `src/build.bats`, over libc, plus the print and exit functions), and empty stubs for the three `libats/libc/CATS` files the C names (`_bats_native_stubs`), and the Makefile compiles with `-D_ATS_CCOMP_HEADER_NONE_ -D_ATS_CCOMP_EXCEPTION_NONE_ -D_ATS_CCOMP_PRELUDE_NONE_ -D_ATS_CCOMP_RUNTIME_NONE_ -include _bats_native_runtime.h -I_bats_native_stubs`, as the wasm build does, with no warning flags turned off. PATSHOME is for running patsopt only; the compiler a normal `bats build` makes still compiles with ATS2's headers.

**The runtime header (its method).** ATS2's own headers (`ccomp/runtime/*.h`, `prelude/CATS/*.cats`) are GPL-3.0-or-later and are not copied into the tree: the repository declares no licence, and copying would carry GPL-3 into it. The header is written here, from the use sites in the C that patsopt emits (the names and shapes in `bootstrap/c`, and in the wasm fixtures' C) and from the semantics ATS2 documents for each name, with its own parameter names, its own bodies and its own structure. The names are ATS2's, since they are the interface the emitted C is written against. Where ATS2 has a macro, this has a macro with another body where the interface leaves one to choose; the arithmetic, comparison and conversion functions of the prelude are typed `static inline` functions made by two helper macros (`BATS_FN1`, `BATS_FN2`), not a copy of ATS2's macros. What each must do: a name that ends a type says which C type it is; `ATSCKpat_con0` is true for the small integer that stands for a constructor without fields, `ATSCKpat_con1` for a pointer (1024 or above, below which are the small integers) whose first word is the tag; `ATSINSmove_con1_new` and `ATSINSfreecon` allocate and free a constructor block with the C library's malloc and free; `ATSfunclo_clo` calls the code address a closure begins with (`cfun`); `ATSINStmp*`, `ATSINSmove_*` and `ATSINSstore_*` are assignments of the shapes their names give; `ATStailcal_beg/end` and `ATScaseof_beg/end` open and close a `do { } while (0)` that `break` leaves (a branch ends in `break`); the `ATSdynload*` macros declare, set and call a module's load flag. How it is tested: the fixpoint (a compiler built from `bootstrap/c` with this header regenerates `bootstrap/c` byte for byte), the whole fixture suite run by that compiler, the wasm fixtures (`tests/build-wasm`, `tests/test-wasm`, which compile with the same text), and gcc compiling every module with no warning flags turned off. `ATS_MALLOC` in the native header exits with a message when malloc answers NULL; the wasm runtime's own malloc is used as it is. The macros of ATS2 that no emitted C names are not defined; the wasm build has always carried the macros wasm consumers (quire's C is not in this repository) might use, so that set is kept, every one written afresh, and a macro found unused by all consumers is a candidate to remove. Copying check (the `#define`s of the generated `_bats_native_runtime.h`, compared with those of ATS2's `ccomp/runtime/*.h`, `prelude/CATS/*.cats` and `libats/libc/CATS`, whitespace ignored, by a script that reads both): 133 defines here, 124 with an ATS2 name; **23 have the same parameters and body**, 40 more agree only up to the names of the parameters, and 61 differ. The residue is the one-line macros whose expansion the interface forces. The 23 are empty or a constant or a keyword or a name: `atsbool_true` and `atsbool_false`, `ATSextern`, `ATSstatic`, `ATSstruct`, `ATSelse`, `ATSbranch_end` (`break;`), `atspre_strlen`, `ATSPMVbool_true/false`, `ATStyclo` (`struct { void *cfun; }`, the field name is the emitted C's), and the empty markers (`ATSdynload`, `ATSbranch_beg`, `ATSextcode_beg/end`, `ATSfunbody_beg/end`, `ATSthen`, `ATSPMVempty`, `ATSINSmove_con1_beg/end`, `ATSINSmove_fltrec_beg/end`). The 40 are one token, a one-token wrapper or a declaration or statement form that has one spelling: the type wrappers (`atstkind_type(kind)` is `kind`), `ATSINSgoto(t)` is `goto t`, `ATSif(t)` is `if (t)`, `ATSreturn(r)` is `return (r)`, `ATStmpdec(n, t)` is `t n`, `ATSstatmpdec(n, t)` is `static t n`, `ATSPMVptrof(p)` is `(&(p))`, `ATSSELfltrec(r, t, f)` is `((r).f)`, `ATSmainats_0_void(e)` is `mainats_0_void()`, the literal wrappers (`(literal)`), `ATSINSmove_void(d, c)` and `ATSINSpmove_void` (`c`, which may be empty), and the empty ones with a parameter. Where another correct formulation exists the macro uses it (a cast spelt once in `BATS_CAST`, `for (;;) { ... break; }` for `do { } while (0)`, a subscript for a dereference, `->` as `.` of a dereference, a tentative definition for an initialised flag, the prelude as typed functions), and the typedefs, the macros and the prelude are ordered by this header's own scheme (alphabetical, grouped by what they do in the emitted C). Whether this residue is acceptable is the owner's decision.

`BATS_REPOSITORY` names the package repository when `--repository` is not given; the flag wins (`tests/repository-env`). The Rust bats had only the flag.

Each command that writes `build/`, `dist/` or `bats_modules/` (check, build, run, test, clean, lock, add, remove, tree, upload) holds the project's lock, `flock(2)` on `bats.toml` opened read-only (file's `fd_lock`), released when bats exits however it exits; a bats that waits for it says `waiting for another bats running in this project`. `bats run` releases it once the build is done, before the program runs. What bats starts inherits the open file, so a patsopt left running by a killed bats keeps the project locked until it ends. Where the file system has no locks, bats runs unlocked. The Rust bats took no lock, so two runs in one checkout wrote one `build/` at once (`tests/project-lock`).

With `BATS_SLOTS` set (1 to 64; a larger number is 64, anything else is said and ignored), `check`, `build`, `test` and `run`'s build also hold one of that many machine slots, after the project's lock: `flock(2)` on `<BATS_LOCK_DIR>/slot-<i>.lock` (`BATS_LOCK_DIR` defaults to `~/.cache/bats`, made when missing), the files and convention of gen-pwa test's `PWA_TEST_SLOTS` and `PWA_TEST_LOCK_DIR` (bats-lang/pwa#82), so one directory given to both is one pool. Each free slot is tried in turn; when none is, bats says `waiting for another bats on this machine (N at once, BATS_SLOTS; <dir>/slot-0.lock was last taken by bats build in <directory>)` (the holder writes that note as the slot's file's first line and clears it as it releases the slot) and waits for slot 0. The kernel releases a slot however bats ends; what bats starts inherits it, as it inherits the project's lock. While it holds a slot, what bats starts gets `BATS_SLOT_HELD`, the slot's file, and a bats that finds that file locked by another open runs in its parent's slot instead of waiting for one (a command make starts runs in its implicit job slot); a `BATS_SLOT_HELD` whose slot no one holds is ignored. Unset or empty, nothing is read, made or said. A directory, file or lock that fails is said, and bats runs without a slot. The Rust bats had no machine-wide limit (`tests/machine-slots`).

With `BATS_PATSOPT_TIMEOUT_S` (wall clock seconds) and/or `BATS_PATSOPT_MEM_MB` (address space, megabytes) set, every patsopt run (`patsopt_only` in `src/helpers.bats`, the one place patsopt is started) is held to them, because the GMP build of ATS2's solver can run away in time and memory on a proof the machine-integer solver answers at once (one function of quire's `library.bats` passed 6.4 GB in 14 minutes, and an earlier run was killed by the system at 9.9 GB with no module named: bats-lang/quire#594). A run the cap ends fails the build with `error: patsopt on src/m.bats was stopped by the time cap: ...` or `... by the memory cap: ...`, naming the module, the variable and its value, and how to raise it, and bats exits 124 (time) or 125 (memory), not 1 as for a patsopt error. Unset or empty, nothing is read, made or said and patsopt is started by bats itself; anything else than a number from 1 up is said and ignored. This is a resource cap on an external process, not a runtime check of the program: the types say nothing of how long or large the solver gets. It is portable sh and kill, which POSIX has, because there is no `timeout(1)` on macOS and the process package has no setrlimit or kill: a capped patsopt is started by `sh -c`, which lowers its address space (`ulimit -v`) and runs patsopt under it; for the time it keeps patsopt as its child and ends it with SIGALRM after the seconds (a `sleep`, ended when patsopt finishes first, so nothing outlives the run or holds the project's lock), telling that death from any other by wait's status 128 + 14. The memory cap has no such sign (RLIMIT_AS only makes allocations fail), so a patsopt that fails under it with a signal, or whose stderr says its allocator or GMP's failed (`ats_malloc_gc`, `Cannot allocate memory`), is the memory cap's; a patsopt error is still one. What is not portable: a system whose sh cannot lower the limit (`ulimit -v` refused, probed once) is told once and patsopt runs without the memory cap, and macOS, whose `ulimit -v` does not enforce RLIMIT_AS, is untested here; the time cap is whole seconds and needs `kill -s ALRM` and `wait` giving 128 + the signal, which POSIX's `kill -14` and every sh tried (dash) do (`tests/patsopt-cap`). Other tools' caps on a prover, for the record: Why3's manual page gives `--timelimit` in seconds (0 off, default 10) and `--memlimit` in megabytes (default none) for each prover call, which is the same pair of wall clock and memory caps; Dafny offers, besides a time limit, a Z3 resource count (`--resource-limit`, a deterministic counter that stops the solver like a time or memory limit, reproducible under load but not uniform in work), which needs a counter inside the solver, and patsopt's has none, so bats caps the process, per module.

A module that staloads `"_bats_facts.sats"` gets `build/src/_bats_facts` (`src/facts.bats`): `bats_commit_time`, `bats_commit_version` (`YEAR.MONTH.DAY.SECONDS` in UTC), `bats_commit_short` and `bats_commit_sha` of the commit `BATS_COMMIT` names, else `HEAD`; outside a git repository, or for a revision git does not know, it is an error that says so. Its `.sats` never changes and its `.dats` is written only when its bytes change, so a new commit compiles that one module again. A project that does not staload it (the name in a comment or a string is not a staload; bats's own sources write it) gets none. `_bats_*` files in `build/src` are bats's own and are not pruned as orphans (`tests/build-facts`). The Rust bats had none.

A module that staloads `"_bats_inputs.sats"` gets `build/src/_bats_inputs` (`src/inputs.bats`, bats-lang/bats#267): `bats_inputs_sha256 (): string 64`, the sha256, as 64 lowercase hex digits, of a listing of the project's own inputs: the line `bats-inputs 1`, then `<path> <sha256 of the file>` for `bats.toml`, for `bats.lock` when there is one and for every `src/**/*.bats`, in byte order of path (`LC_ALL=C sort`). It reads no git and no clock, so the same bytes give the same digest in any directory, with any mtimes and at any commit, and a dirty tree has an honest one; the dependencies' archives are named in `bats.lock` by their sha256, so the lock stands for them. Its `.sats` never changes and its `.dats` is written only when its bytes change, so a changed input compiles that one module again. A file that cannot be read is an error that says so. A project that does not staload it (the name in a comment or a string is not a staload) gets none and runs nothing; `_bats_*` files are not pruned as orphans. bats's own sources staload it and do not use it yet (the identity of this bats, for the stamp of a `build/` to come). The Rust bats had none (`tests/build-inputs`).

`build/` carries a stamp of who made it, and is kept only when the running bats would write the same one (`src/stamp.bats`, bats-lang/bats#267). `build/.bats_stamp` is plain text, `bats-stamp 1` and then `name value` lines: `bats` (the `_bats_inputs` digest of the running bats's own sources, which bats's own source staloads), `patsopt` (the sha256 of the cksum listing of `bin/patsopt`, `prelude`, `libats`, `share` and `ccomp` that `BATS_CACHE_DIR`'s key also uses, `toolchain_digest` in `src/cache.bats`, made at every build now and not only with that variable set), `cc` (the sha256 of `clang --version` and `clang -dumpmachine`, and of `wasm-ld --version` for a wasm mark, without the lines that name the install directory), `flags` (the flag templates patsopt and cc run with for the mark, `PATSHOME` written `$(PATSHOME)`, both profiles in one template since a `build/` holds both) and `mark` (the target and mode digit of `build/.bats_target`). No line holds a path, so a `build/` copied to another directory, or made on another machine with the same bats, ATS2 and C compiler, keeps (bats-lang/bats#250 made the C path-independent). After `cache_swap` has put the mark's `build/` in place (from its stash if it had been put aside: every stash carries the stamp of whoever made it, and is judged when it is swapped in), `check`, `build`, `test` and `run`'s build compare the stamp they would write with the one in `build/`. Equal: `build/` is kept, and a build that finds nothing changed runs no patsopt for the modules (the entry's generated module is still made again, as before). Different or missing: everything in `build/` but `.stash` is removed, one line on stderr names the first line that differs (`bats: dropping build/ (made by another bats: patsopt differs)`; `no stamp`, `the stamp format differs`, `mark differs` and `the stamp differs` are the others), and the build starts from nothing. A `build/` with no stamp, every one made before this, is dropped once; one that holds no build (no `.bats_target` and no stamp) is not dropped and says nothing. This replaces the hand-bumped `build/.bats_cache_id` (`cache_buster_id`), which went with the removal of every `.o` that it and a changed target caused: with the stamp that removal is dead, since `build/` is empty or this mark's by then (`target_changed` stays as the belt for an unreadable marker). The Rust bats had no stamp, so a `build/` of another compiler was trusted if its mtimes were right. `BATS_CACHE_DIR`'s key begins with the same `bats` digest, where it had the hand-bumped `patsopt-1` (the directory of the entries keeps that name, so entries of older bats are trimmed after 7 days as before). The test is `tests/build-stamp`.

`bats fixtures <dir> [--only <member>]... [--cold] [--work <dir>] [--memo <dir>] [--prune] [--repository <dir>]` (bats-lang/bats#267, item 4: quire's static-test runner, `tests/static/run.sh` and `expect.py`, folded into bats; `src/fixtures.bats`, `tests/fixtures`) runs a directory of fixtures against a copy of the project (the current directory). A fixture is `<dir>/accept/<name>/` or `<dir>/reject/<name>/` with `file` (the project's module, from its root), `before` (a line of it), `snippet.bats` and, for a reject, `expect`; the snippet is put into the module followed by one blank line, before the first line that is exactly `before` (no such line is a failure of the fixture), because what a fixture tests is private to its module. The project is copied to `<work>/app` (everything but `build`, `dist`, `.git`, `node_modules` and `test-results`) and checked whole first with `bats check` (the program as it was run; the fixtures mean nothing if it does not check, so the run fails and no fixture runs), its `build/` kept in `<work>/build-checked` and put back, with the module, after each fixture: each starts from the project as the check left it, so only its module is checked again (with the freshness and the stamp bats already has: nothing is re-implemented here). `--work` keeps the directory (CI restores its `app/build` between runs); without it a `mktemp -d` one is made and removed. An accept passes when `bats check` passes. A reject must fail it exactly as its `expect` says (`expect.py`'s rules, ported to bats): `function <name>`, `line <n>`, then patsopt's error as it says it (its message after `error(N): ` and the lines it adds to it, up to patsopt's summary, bats's own `error:` lines, `exit(ATS)`, a blank line); an expect that is not that form (two lines, another word, a line that is no number, empty, absent) is a failure of the fixture, never a pass; the declaration (`fn`, `fun`, `fnx`, `prfn`, `prfun`, `implement`, `val`, `var`, `and`, then `{...}` groups, then a name) enclosing line `n` of the snippet must be `<name>`; there must be at least one patsopt error, each in the module `file` (its path ends with `/` and the module) and at snippet line `n`; and their text, line for line, must be the expect's, with only patsopt's variable numbers compared as `_` (`S2EVar(N->`, `$N(` and `S2Evar(name(N))`: not the constants, not a number of another form). A substring that another error could also hold is not enough. The output is one line per fixture as run.sh printed it, `ok   accept/<name> (N s)` or `FAIL reject/<name>: rejected, but not as its expect says: <why>` (followed by the patsopt lines that name an error), then `fixtures: N ok, M failed`; the status is 1 when anything failed, 2 for a usage error (an unknown option, no directory or two, an `--only` that names no fixture: a member is `accept/<name>` or `reject/<name>`). `--only` is repeatable. `--cold`, `--memo` and `--prune` are the memo's (next paragraph). What the system does that bats does not (copying the tree, putting the lines of the snippet in, running `bats check` with its output in a file, `date`, `mktemp`) is `sh`, `tar`, `head`, `awk` and `tail` run by the process package, as `src/cache.bats` runs `sh`; which line, and what the output means, are decided in bats. The program run for the checks is the one that was run (`argv[0]`, resolved to a path when it has a `/`, else through the PATH); `GIT_DIR` is taken from the project's repository for a module that staloads `_bats_facts`. What the types prove, and what is a branch on the data instead of a proof: every read of a text is proved in range (a text's length is `tlen`, `[n:nat | n <= 524288]`, from `read_text`, whose answer is `[k:int | ~1 <= k; k <= 524288]`: the file's length or ~1; `text_len` maps the ~1, which the caller has already said as a failed read, to an empty text), `text_has` and `step_text` check that the text lies inside the buffer before comparing and answer a position the types bound, `step_digits`, `header_parse` (a position of the line it returns is proved between the line's start and the text's end, by the chain of its 14 steps, each in the success branch of the one before), `trim_end`, `trail_blank`, `variable_end` and the rest return positions or lengths indexed by the bounds they keep, so no clamp of a length or a position remains (the `clamp_len`, `put_between` and `put_text` of the first version are gone). What is still a branch, and no proof: the orderings that depend on the text read (`ns <= e1`, `ls <= e2`: whether the expect's first line is longer than "function "; `ne >= ns` in `decl_is`; `r > p` and `r <= len` in `variable_end`, where the end of a match is computed from bytes through plain ints and `g1ofg0`; the `p15 <= b` end of a header), each of which decides the answer (not a header, not that function, no variable) and none of which a proof could replace without the text being known; and the offsets of the settings buffer (`g1ofg0` of a builder's length). Differences from `expect.py` (Python), in the direction of failing a fixture, except two cases where this accepts what Python does not: an expect that spells literally a message containing `\x0c`, U+2028 or a line of NBSP alone, as the log has it, is ok here and fails in Python (which splits the log there), and a `file` padded with spaces or other whitespace is stripped here (as `expect.py` strips it) while run.sh's raw `cat` of it would not find the module: an expect with CRLF line ends fails here (its lines keep a `\r`) and passes in Python only if the snippet's error does too; `int()` of the line accepts `+1` and `1_0` in Python and is digits only here (a `+` or `_` is a malformed expect); whitespace (`strip`, the space after the function) is ASCII only (space, `\t`, `\n`, `\v`, `\f`, `\r`, `\x1c` to `\x1f`), so NBSP, `\x85`, U+2028 and U+2029, which Python's `str.strip` and `splitlines` also take, are not; a log is broken at `\r\n`, `\r` and `\n` as `splitlines` does for those, but not at `\x0b`, `\x0c`, `\x1c` to `\x1e` (control characters patsopt does not print). A directory with no fixture in it (not there, empty, or only empty `accept` and `reject`) is a usage error (status 2), so a mistyped path in CI fails. The work directory is excluded from the copy of the project when it is inside it (`--work ./w`), and the check's log and seconds are removed before each fixture, so a snippet that could not be put in is a failure of that fixture, never judged against the last one's log. The texts are at most 524288 bytes each (a log, an expect, a snippet), the module at most what an arena holds. `bats fixtures` is read before bats's own arguments, as `with-env` is. Python's `splitlines` breaks a log at `\r` too, and so does the matcher (`\r\n` as one); `str.strip` is ASCII whitespace here. Tests: `tests/fixtures`.

**The fixtures' memo** (bats-lang/bats#267, item 4b; `src/fixtures.bats`, `tests/fixtures/check.sh`). A fixture whose result was kept is not run again when everything its check reads is as it was. The output keeps quire's shape, `ok   accept/<name> (N s)`, and a fixture served from the memo says `ok   accept/<name> (0 s) [memo]` (the marker after the seconds, so a reader that matches `ok   <member> (N s)` still does), and the last line gains ` (K from the memo)` only when K is more than 0. *Key* (sha256 of a text of seven lines, kept in the entry): the module's path from the project's root, the sha256 of `before`, of `snippet.bats`, of the module with the snippet in, of `bats.toml`, of `bats.lock`, and of `build/.bats_stamp` (the bats, patsopt, C compiler, flags and mark: the toolchain). No path of a checkout is in it (a project at another path, a memo copied elsewhere, hit). The `expect` is not in it. *Entry* (`<memo>/<2 hex>/<key>`, a text): its format line, the key, `pass` or `log`, the sha256 of the sorted names of every `.sats` and `.hats` of `build/` (not the stashes' nor the digests') and of every `.bats` of `src` and `bats_modules` (a module added or removed: what patsopt might read instead of a file, as the check memo's `names`), then one line for each file the module's check reads: `R <sha256> <path>` or `C <sha256> <path>`, then the log, then the key's text, then `sum <sha256 of every line before>`. The files are those of the module's `build/src/<m>_dats.c.key` in the checked base (bats#298's list, which `patsopt --depgen` followed to the end made) less the module's own `.dats` and `.sats` (the module with the snippet in stands for them in the key); if the module's own `.sats` with the snippet in has another digest than the base's (the snippet changed the interface), the lists of every module whose base key names that `.sats` are in too (a dependent can fail on what the snippet changed). A `.sats` is digested as its text with each run of line feeds as one (the interface, as the check memo digests it; a file with a quote, a percent sign or a char in it is digested as it is, since a line feed may be part of what it says), any other file as it is. Nothing reads a time: a file is the same when its digest is, never when its size or its mtime is. *Lookup*: an entry is served when it is a regular file (not a link), its sum is right, its first line, key, kind (an accept is served only a `pass`, a reject only a `log`), names and the number of its lines are right, and every file it lists has the digest it holds; anything else is a miss and the fixture runs. A directory is a memo only when it holds the mark `.bats-fixtures-memo`, which the first store makes in an empty directory; bats neither reads from nor writes to another (a mistyped `--memo` is not filled, nor pruned). *What is kept* (after a run, never before): an accept that passed, as `pass`; a reject whose check failed the ordinary way (status 1 and a line `...: error(N): ...` of patsopt's, a log of at most 524288 bytes), as `log`, the log as bats printed it with the work directory's path written `/app/` and the lines that vary with the machine dropped (`waiting for another bats`, the warning about an ATS2 bats did not install). A reject's entry holds the log, not a verdict: the expect is judged against it at every run, hit or not, by the same matcher, so a changed or wrong expect, or a fixed matcher, takes effect with no patsopt run. Never kept: an accept that fails, a reject that passes, a check that fails with no patsopt error (a refusal before patsopt, a status 124 or 125 of a cap, a signal), a fixture that could not be put in, and a snippet that names `load`, `include`, `#use` or `#require` anywhere (it reads a file the base module's list does not name; it is checked at every run). An entry is written beside its place (`.tmp.<key>.<pid>`) and renamed into it: no lock, a reader sees a whole entry or none, two writers of one key write the same bytes, and a run killed while it checks writes nothing (the entry is the last thing a run does). *Where*: `--memo <dir>`, else `BATS_MEMO_DIR`, else `$XDG_CACHE_HOME/bats/fixtures`, else `$HOME/.cache/bats/fixtures` (ccache's default is `~/.ccache`, or `$XDG_CACHE_HOME/ccache` when it is set; Bazel's disk cache is opt in; `BATS_LOCK_DIR` here defaults to `~/.cache/bats`): sharing between checkouts and worktrees is the point and the key holds the toolchain, so it is sound; a CI job caches the directory alone (GitHub's cache is immutable per key: restore the newest `restore-keys` prefix, save under a new key when entries were added). *`--cold`* (or `BATS_COLD` set to anything but `0`) reads no memo and runs every fixture, writes the memo, and is an audit: when the memo had an entry that would have been served and the cold run says otherwise (an accept the entry says passes and now fails; a reject whose log, as kept, is not the cold run's) the fixture is `FAIL <member>: STALE MEMO: <why> (key <key>)`, the status is 1, and the entry is removed, so a key that missed an input shows as a red run (main's run is meant to be cold, as the check memo's). The base check and the fixture's check under `--cold` are bats's own incremental ones (only the memo is cold). *`--prune`* (not with `--only`, status 2) after the whole set has run removes the entries of the memo that no fixture of the run used, one line `pruned <2 hex>/<key>` for each and `memo: pruned N entries, kept M`, and temporary files of a writer whose pid is gone (`kill -0`; not a time); it touches only regular files named by a key in a two-digit directory of the memo (not through a link), only in a marked memo.

What is done in sh and what is not proved. The memo's lookup, store and prune are one `sh` script that `bats fixtures` writes to `<work>/memo.sh` (a literal of `put_memo_script`) and runs with the process package, as the rest of this command runs `sh`, `tar`, `head` and `awk`: bats has no sha256 of a tree, `find` or `kill` of its own, and the files it reads are the system's. Hashing is `sha256sum`, or `shasum -a 256` where there is none. What is decided in bats is unchanged (the matcher, the output, the counts, the usage). What is not proved, and is tested another way: that `patsopt --depgen`'s list (bats#298's) names every file a module's check reads; that the validation of the whole project that runs before patsopt (`validate_project`: the call-cycle check reads every `.bats` of the package, so a cycle through an `implement` of another module could make a fixture fail that the memo served) is a function of the module's closure: it is not, the key has the names of the `.bats` but not their contents, and `--cold` is the detector for it (the cost of the alternative, every source in the key, is a memo that no change to any module survives); that the digest of a `.sats` as an interface means what the file means. `tests/fixtures/check.sh` plays: a second run served wholly with no patsopt on a fixture, the key with no absolute path, the three ways to name the directory, an unrelated module changed (not run), a module that reads the module's interface changed in its body (not run), the module changed (run), a staloaded `.sats` changed to one of the same size (run), a module added, a changed snippet and `before`, a changed toolchain, a changed or wrong expect (judged again, no patsopt), a stored log doctored (judged, and found stale by `--cold`), a memo that lies (found, dropped), a truncated, garbled, foreign, other-format, shortened or other-kind entry, failures that are never kept, a snippet that loads a file, a dependent that changed after a reject on an interface the snippet changed, a run killed in its check, four copies of the project over one memo for five rounds (some of them cold) and `--prune`. Found on the way, not fixed here: `build/.bats_toolchain` is trusted across processes whatever `patsopt` now is (an edit in place is not seen by the stamp until the file is removed), which the stamp of #273 was to prevent.

The generated Makefile (`bootstrap/c`, `--to-c`) has `make install`, which puts the compiler at `$(PREFIX)/bin/bats` (`PREFIX` defaults to `~/.bats`).

`bats with-env <env-file> <command> [args...]` (bats-lang/bats#277, a subcommand, the owner's ruling: bats has subcommands, not scripts) gives a shell that reads no profile (an agent's, a CI-like step) a machine's bats settings (`BATS_SLOTS`, `BATS_LOCK_DIR`, `BATS_CACHE_DIR`, `BATS_REPOSITORY`, and whatever else the machine sets, such as pwa's `PWA_TEST_SLOTS`): the file's variables are added to bats's environment (the file wins over the caller's) and the command is run with the arguments exactly as given and the standard streams shared; its exit status becomes bats's own. It is read as a dotenv file, not sourced by a shell (`src/with_env.bats`): `NAME=VALUE` or `export NAME=VALUE`, `#` comments, a value bare, in single quotes (literal) or in double quotes, `$NAME` and `${NAME}` taken from the caller's environment (so `PATH=/opt/bin:$PATH` works), a variable set twice has its last value, nothing else interpreted. It is read before bats's own arguments, so the command's own flags (`--help`, `--`) are its alone. Comparable tools: `env -S`, direnv, `dotenvx run` and `docker run --env-file` set the environment of one command from a file and run it; docker's and systemd's do not expand, dotenvx and Compose do. `tests/with-env` plays it.

Exact rules of the file and the command (all `tests/with-env/check.sh`):

* The file is at most 64 KiB (65536 bytes is read, 65537 is refused) and sets at most 1024 distinct variables. Which line is a variable's last is found in one pass over the file with a table of the names (a first version asked every line whether a later one overrode it: a 64 KiB file of comments took over a minute); the 1024 is because the process package's argument is an array of 512 KiB, so a variable costs about 130 KiB of memory and a tenth of a millisecond, and 7000 of them (all a 64 KiB file can name) took 1 GB and 3 seconds. 1024 is also far above any machine file's size: comparable tools set no count, so this is a bound bats needs and others do not. A file of 64 KiB of comments, or of one variable set on every line, takes no time.
* Nothing is cut short, and, beyond the caller's own environment, nothing is made that exec would refuse late (the kernel's total counts the environment bats inherits too: a caller with 14 variables of 120000 bytes makes exec fail with 126 "Argument list too long" for a file well within the 524287). A name inside `${...}` over 255 bytes, a variable of the caller's whose value is over 64 KiB, an entry (`NAME=VALUE`) over 131071 bytes, and entries that together take over 524287 bytes (each with the NUL after it) make the whole run a usage error, status 2, naming the variable of the file that was being made (for the total, the variables are counted from the last of the file backwards and the one named is the one that crossed the limit). The limits are checked as the entries grow (a value is not copied when it would not fit), so a file that cannot work fails at once: 1024 variables each with `$BIG` five times, BIG being 64 KiB, took 26 s and then failed in exec with "Argument list too long". Where the numbers come from, as separate facts: (1) **the process package**: `spawn_inherit_env_with` copies the extra entries into one builder of 524288 bytes, a NUL after each (`_build_from_list`), and answers E2BIG when they do not all fit, which is `sum(len + 1) <= 524287`; `spawn_child_with` would put a `BATS_SLOT_HELD=<path>` entry first when this process holds a machine slot, but with-env holds none (it runs before bats takes any), so the whole 524287 is the file's. 4 entries of 131071 bytes were a late "cannot run: Argument list too long" (126) before this was budgeted. (2) **Linux** refuses an exec whose single argument or environment string is over MAX_ARG_STRLEN, 32 pages, 131072 bytes with the NUL (include/uapi/linux/binfmts.h; E2BIG), so 131071 is the kernel's own bound on one entry; and whose strings together are over a quarter of the stack limit (8 MiB by default, so 2 MiB, at most 6 MiB since 4.13; glibc's ARG_MAX says the same, at least 128 KiB), counting the arguments and the inherited environment too (mina86.com/2021/the-real-arg-max-part-2, kernel bug 10095, the LKML thread on raising MAX_ARG_STRLEN to 6M, which I could not find merged). (3) **macOS** has ARG_MAX of 1 MiB for arguments and environment together (`sysctl kern.argmax` is 1048576), so the package's 512 KiB leaves the rest to the caller's environment there. Docker (`--env-file`), Compose, dotenvx and systemd's EnvironmentFile document no limit on the number or size of the variables in a file that I could find (searched; Sitecore's Compose setup asks for 30,000 bytes a variable, which is its own); they pass the variables to the runtime and the kernel refuses. A value is read into 65537 bytes, hence the 64 KiB per expanded variable. Only the effective (last) line of a variable is expanded, so an overridden line cannot fail. A `${` takes any text up to the next `}` as the name, so `${a b}` is the variable named `a b` (unset: empty). The tests assert both edges (`tests/with-env/check.sh`: an entry of 131071 bytes runs and 131072 is refused; entries totalling 524287 run and 524288 are refused).
* A NUL byte in the file is a usage error naming its line (a NUL would end a name or value early in the C strings exec takes, so the rest of the line would be dropped or, after a newline, a variable injected); the file must be text.
* Corners, decided by what the comparable tools do and kept simple: a `# comment` after an unquoted value is part of the value (docker run --env-file: a `#` anywhere but the start of a line is part of the value, its documentation says; only a line that starts with `#` is a comment); an unbalanced quote (`A="x`) stays in the value as written; `\$` is not an escape, it is a backslash followed by an expansion; a `$` that starts neither `$NAME` nor `${NAME}` is a `$`; a line of another shape is passed over; CRLF line ends are accepted (the carriage return is not part of the value).
* The command line is read whole into 4096 bytes: argv[0] (bats's own name or path), `with-env`, the file, the command and its arguments, each with the NUL after it, must be at most 4095, else status 2.
* A command name with no `/` is looked for, as the shell does, in the directories of the PATH the command will run with: the file's `PATH` when it sets one (expanded as every value is), else bats's own; empty or unset is `/usr/bin:/bin` (as the process package's execvp does), an empty entry is the current directory. The first file that is not a directory and has an execute bit wins; a directory, or a file with no execute bit, is passed over, and when nothing better is found the status is 126 ("Permission denied"), not 127. The process package would look in bats's own PATH only (it calls `execvp` after the environment is fixed), so with-env finds the file itself (`file_exists`, `file_mode`, `dir_open`) and gives it the path; a command with a `/` is run as named. An execute bit is any of the three, not whether this user may run it: a file only another user may run is chosen and fails with 126.
* Statuses: a usage error 2; a command found nowhere 127; one that cannot be run 126, with the system's reason (`strerror` through the process package's `os_error_text`: "Permission denied", "Exec format error").

**What with-env's types prove, and its silent defaults (a deviation from "never add runtime checks"):** In `src/with_env.bats` every read of the file's bytes (`read_byte`, `$A.read` with a proof `p < n`), every write into a name (`write_byte`), every use of the table with an index (`p < 6144`), every span (`[a,b,v:nat | a <= b; b <= n; ...]`, in `same_span` too: its bytes are read only where `a + j < ae <= n`, and it has no default for running out) and every entry number is proved by its types, from `line_assignment` on; the hash is `nmod`'d and bytes go through `$AR.low_byte`. What is not proved, said exactly:
* `table_read` clamps. The ints of the one-pass table (spans, chain links) are written as ints and read back as ints, and a value read from memory has no index in its type (the array package has no content-indexed int array: bats-lang/array#49), so it takes a value outside its bounds `[lo, m]` to be `lo`. It cannot happen (every value written is a position or entry number already in range). It is the only clamp of a value.
* `chain_find` stops, answering "not found", after 1100 steps (`fuel`). A chain of entries is linked by ints read from the table, and the types cannot say the chain ends (it does, since a link is always to an earlier entry, and there are at most 1024); the termination metric needs a bound, so the fuel is one. Without array#49 it stays.
* The builder writers of `src/helpers.bats` (`put_char_v`, `bput_v`, `copy_to_builder_v`) drop a byte that does not fit a full builder (524288 bytes) without a word. Every builder of this module stays far below that, by arithmetic in the code and not by the types: an entry over 131071 bytes is refused (status 2), never cut (the entry builder can briefly reach about 192 KiB (196607 bytes), 131071 of expansion plus up to 64 KiB of literal text, before that check), a name at 255, a value read at 65536, a command line at 4095, a path at about 130 KiB.
* `put_expanded` reads the byte after a `$` only when there is one (`p + 1 < n`) and takes none as "not a `{` and not a name", so a `$` at the end is a `$`; that is a branch in the code, not a default of a reader.
* `prerr_seg` (`put_seg` in `src/helpers.bats`) clamps silently: an index below 0 is read from 0, an index above the buffer's length prints nothing, and a length past the buffer's end stops at its end. It prints only with-env's error messages, which are diagnostics; no result of a command depends on it.
* Some end-of-buffer branches are unreachable and fall through silently, each excluded by the bound of the line that reaches it: `put_expanded` (`p + 2 > n`, which gives a literal `$`; `p + 1 < n` is checked first), `put_expanded` (`close + 1 > n`; `close < b <= n`), `table_fill` (`e + 1 > n`; `e <= size <= 65536 < n`), `arguments` (`z + 1 > 4096`) and `run_command` (`command_to + 1 > 4096`).
Everything else that was a clamp is gone: `byte_at`, `peek` and `poke_arr` of the helpers (which return 0 or ignore a position out of range) are no longer used here.

**What with-env cannot do yet, because of the process package (it owns the platform; bats adds neither `$UNSAFE` nor C):**

* **bats does not replace itself with the command, so a signal to bats does not reach it.** The script this replaced `exec`ed. Now `kill <bats>` (SIGTERM, SIGHUP) ends bats and leaves the command running, orphaned. with-env takes no project lock and no machine slot itself, but what the command starts (a `bats check` in it) does, and it keeps them until it ends. A terminal's Ctrl-C reaches both, since both are in the foreground process group. The process package has `spawn`, `child_wait`, `child_try_wait` and `child_pid`, and no `exec`, no `kill` and no signal handler; the env package has none either. The need is an `exec` that replaces the process (the platform's `execve`: Rust's `CommandExt::exec`, Python's `os.execve` and Go's `syscall.Exec` are the same call), which also removes the next limit. The need is filed as bats-lang/process#51; until it lands the limit stands, and `tests/with-env/check.sh` expects the orphan and fails when the signal does reach the command, so the change to exec is noticed.
* **A command a signal ended has status 1, not 128 + n.** The process package's `child_wait` returns the exit status when `WIFEXITED` and the same ~1 for a signal death, which cannot be told from a failure to wait, so a shell's convention (128 + the signal, which `sh`, Python's `subprocess` shell and `env` report) cannot be had; Rust's `ExitStatusExt::signal()` and Python's negative `returncode` are the platforms' way of keeping it. Filed as bats-lang/process#52 (what is needed: a `child_wait` outcome that says exited with a status or ended by a signal number). With `exec` the shell that started bats sees the real death and this limit goes away too.

These are the only allowed divergences. All other flags and behaviors must match the old Rust bats exactly.

## Safety Enforcement

Unsafe constructs (`castfn`, `$extfcall`, `$extval`, `$extype`, `$extkind`, `praxi`, `extern`, `assume`, `mac#`, `ext#`, `while` (`while*` with a metric is fine), `fun`, `fnx`, a `fun` group's `and` member or `fix` without termination metric (the `fun` of an arrow, `=<fun>`, is a function kind, not a declaration), `val rec`, `#pub prfun`/`prfn` without `primplement`, and what allocates without being linear: a `datatype` whose constructor carries data, a boxed tuple, record or list, a `cloref` or `cloptr` closure, a `lam` whose arrow does not make it a plain function or a linear closure, a `ref` made inside a function, a prelude word that builds a non-linear list, option or stream, libats/ML) are detected by the lexer (`SConstruct`, or a rejected `SPub`) and **enforced** before patsopt runs (`validate_project` in `src/lock.bats`, Rust's `preprocess_all`), as is the rule that no `implement` is on a call cycle (`src/recursion.bats`). They, and `%{ ... %}` blocks, are rejected outside `$UNSAFE begin...end` blocks in ALL packages — both safe and unsafe. `$UNSAFE begin...end` blocks themselves are rejected in `unsafe = false` packages.

## Problem Resolution

A problem already existing is never a good reason to ignore it. Problems must be fixed. Safety problems must be prioritized.

## Safety Philosophy

Never add runtime checks (assertions, bounds checks at runtime, abort-on-overflow). The type system must prevent bad states at compile time. If you cannot prove safety statically, the API is wrong — fix the API, don't add a runtime check. Runtime checks are a sign that the type system is not being used correctly. The whole point of ATS2 and Bats is that safety is enforced by the compiler, not by runtime guards.

Segfaults must never happen. A segfault means something is fundamentally wrong — do not work around it, do not accept it, do not split files to avoid it. Find the root cause and fix it systemically. If it's caused by unbounded recursion, figure out how ATS2 is supposed to handle this (it has tail-call optimization). Use web search to understand the correct solution. Do not settle for less than correct.

Don't guess. Don't "try" things. Read the code. Carefully reason about what is happening. Understand before acting.

Do not assume Linux. Code must be portable (macOS, Linux, BSDs). Do not use `/proc/self/exe` or other Linux-specific paths.

Do not use bats-old unless it's an emergency. The self-hosting compiler is the primary build tool.

Fix problems regardless of size. Never say "too large for this session" or defer work. Do the work.

## Task Rules

A task should never be more than one thing: if it requires the word "and", for example, it should be broken up. If it refers to plurals, it should be broken up. If it has a comma, it should be broken up.

## CI is pinned

Every input to CI is pinned in the source (bats-lang/repository-prototype#269),
so a commit that passes keeps passing:

* `bats.lock` is committed, and CI unpacks exactly the locked versions.
* The seed compiler is `bootstrap/c`, in the tree.
* The package repository is fetched at the commit in
  `.github/repository-version`, so what the fixture tests under `tests/`
  lock (`bats lock` against it, e.g. `lock-namespace`) is pinned too.
* `relock-pins.yml` in bats-lang/repository-prototype is called by commit.

Pins move only through a reviewed pull request that runs the same CI.
The daily `relock.yml` (the shared `relock-pins.yml`) relocks against the
newest repository, moves `.github/repository-version` to it, pushes
`relock/<date>`, opens a pull request listing the old and new versions
and dispatches `check.yml` on it, so a breaking publish shows as a red
relock pull request and main stays green. GITHUB_TOKEN cannot change
workflow files, so without a `RELOCK_TOKEN` secret that pull request lists
a workflow pin that would move instead of moving it.

## The setup step other bats repositories call (#274)

`.github/actions/setup/action.yml` is the one step a bats repository's job
runs first, called by commit: `bats-lang/bats/.github/actions/setup@<40 hex
digits> # <what it is>` after a checkout (two commits deep, `fetch-depth: 2`,
when the version is a pull request's head). It installs, on an apt runner,
the GMP build of ATS2 (`ATS2-Postiats-gmp-0.4.2`, its tarball checked
against a SHA-256 written in the action: the `-int` build accepts false
statements, quire#594), `libgmp-dev` and `lld`; builds the compiler from the
checked-in `bootstrap/c` of the commit `.github/bats-version` names
(`bats-version` overrides, `profile` is `release` or `debug`) and puts it on
the PATH; clones repository-prototype at the commit
`.github/repository-version` names (`BATS_REPOSITORY`); sets
`BATS_PATSOPT_TIMEOUT_S` and `BATS_PATSOPT_MEM_MB` (600 and 4096, inputs);
and sets `BATS_COMMIT` to `commit`, which defaults to
`github.event.pull_request.head.sha || github.sha`, so the version names a
pull request's head, not the merge GitHub tests, and a merge group's own
commit. It refuses before installing anything: a pin that is not a full
lowercase SHA (never a branch or a tag; a missing pin file is an error, not
the newest), a `commit` not in the checkout, a project with no `bats.lock`
(`require-lock: 'false'` for a package with no dependencies). It installs and
keys no cache: a `build/` is kept or dropped by bats itself (#267).

Its test is the `setup-action` job of `check.yml`: the three refusals, then
the action on `tests/setup-action/project` with the compiler built from the
commit under test, and `tests/setup-action/verify.sh` (GMP patsopt linked to
libgmp, lld, the caps, the repository at its pin, `BATS_COMMIT` the head and
not the merge, and a build of the project whose facts name that commit).
`scripts/check-pins.sh` (tested by `tests/setup-action/pins-check.sh`, both
the first step of the `check` job) fails any `uses:` of a workflow or action
that is not a local path or a repository at a full commit SHA followed by a
comment naming the version. A change to the action is called by its new
commit only after this repository's CI has passed on it.
