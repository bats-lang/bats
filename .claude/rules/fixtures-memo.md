# The fixtures' memo

**The fixtures' memo** (bats-lang/bats#267, item 4b; `src/fixtures.bats`, `tests/fixtures/check.sh`). A fixture whose result was kept is not run again when everything patsopt reads for it is as it was. The output keeps quire's shape, `ok   accept/<name> (N s)`, and a fixture served from the memo says `ok   accept/<name> (0 s) [memo]` (the marker after the seconds, so a reader that matches `ok   <member> (N s)` still does), and the last line gains ` (K from the memo)` only when K is more than 0. **A hit stands in for patsopt's answer on the spliced module and for nothing else**: for every fixture, after the snippet is put in and before the memo is asked, `validate_clean` (`src/lock.bats`, the body of `validate_project` without its report: the lexer's rules and the call cycles of every `.bats` of the package, which have no patsopt in them) runs on the project as the check would see it, and a project it refuses is not looked up (the fixture runs, and `bats check` says why). The first version of this memo asked first, so a cycle through another module's `implement`, made after an entry was kept, was served as a pass (the review of bats#303); `tests/fixtures/check.sh` ("a hit stands in for patsopt's answer") plays it. The price was the validation itself: it lexed every `.bats` file of the project and its dependencies twice for each fixture (on quire about 100 s of a 115 to 145 s warm check, measured on a loaded machine). It now reads what `validate_project` already judged (`src/validated.bats`, bats#296): the base check of the run leaves a record for each file that passed under `build/.bats_valid` of the copy, each keyed by the sha256 of the file and of the context (bats's inputs, the packages installed, whether the package is unsafe), and `validate_clean` is the same function with the same records, so a fixture lexes only what its snippet changed (the one module) and the call cycles of `./src` again (the files of the package that an earlier fixture of the run scanned with the same bytes are not lexed again: recursion.md) (that record's key holds every source file's path and sha256, so a cycle made by a later change in another module changes the key and is looked for: the case in `tests/fixtures/check.sh`). The dependencies' files and the dependencies' cycles are not lexed again. Nothing reads a time. The check memo of #298 has no such hole: `validate_project` runs in `bats.bats` before `do_check`, and its memo sits inside `do_check`, so the same project is refused by `bats check` with every module warm (a case of the same test). The `expect` is not in it. *Writes* are plain: the file package has no rename, so no file is written beside its place and moved. What takes the place of the rename is that a reader trusts nothing it has not checked: a torn `.res` fails its sum, a torn `.key` fails the `.res`'s digest of it, two writers of one key write the same bytes (the key says what is in them), and a run killed while it checks has written nothing (the entry is the last thing a run does). There is no liveness check (no `kill -0`, no time). A reject's entry holds the log, not a verdict: the expect is judged against it at every run, hit or not, by the same matcher, so a changed or wrong expect, or a fixed matcher, takes effect with no patsopt run. Sharing between checkouts and worktrees is the point and the key holds the toolchain, so it is sound. *`--cold`* reads no memo and runs every fixture, writes the memo, and is an audit, a re-verification (the validation above is not left to it): so a key that missed an input shows as a red run (main's run is meant to be cold, as the check memo's).

**What a writer digests (bats#480).** The `.res` names the sha256 of the `.key` bytes the writer
holds (`store_in` digests the closure text it just wrote, `put_sha_range` over the same builder
`path_write` wrote), never of a read-back of the `.key` file: another writer of the same key opens
the file with truncation at any moment, so a read-back can be empty or partial and would name a
digest no `.key` has, a lost entry (a miss on every later run, until some run stores the key
again). Two writers write the same bytes, so they name the same digest. `tests/fixtures/check.sh`
("memo truncated key") plays the truncation between the write and the digest with a FIFO.

What is done in sh, and what is not proved. The memo is all in bats: the lookup, the store, the audit and the prune use the file package (`file_read`, `file_write`, `dir_read`, `file_chdir`, `file_mkdir`), the path package, the `sha256` package, `src/cache.bats`'s key and `src/lock.bats`'s `validate_clean`, and the command has no `sha256sum`, `shasum`, `find` or `kill` of its own. What is still `sh`, and is not the memo's: `splice_snippet` (`head`, `awk`, `tail`, `mv`: putting the snippet in a module), `run_check` (`cd app && bats check`, its output in a file, `date`), `restore_copy` and the copy of the project (`tar`, and a `find` that empties the copy), all from #297, as the rest of this command runs them; the memo adds none. Its one external program is `rm -f` of a file, through bats's own `remove_output_m` (in `src/helpers.bats`, given the path's length; an `exec` of `rm`, not `sh -c`, as the compiler's cache removes a stale output): the file and process packages have no unlink. Why those stay: the file package has no rename, unlink or copy, and the process package starts a program, so the copy of a tree and the removal of a file are the system's; the avenues that were open do not reach: `file_write` writes a whole file and cannot append or rename (the memo works around the missing rename with a checksum, above); the process package cannot give a child another directory other than by `sh` (hence `cd app`); `dir_read` lists a directory but names no file type, so the prune removes only files it names by a 64-digit key and `.key`/`.res`, from a subdirectory that holds a mark, and the refusal of a link is tested (`check.sh`, "--prune"). A small package change (rename and unlink in the file package, a `cp -R`) is the right place to remove this residue; no package was changed here. What is not proved, and is tested another way: that `patsopt --depgen`'s list (bats#298's) names every file a module's check reads; that the digest of a `.sats` as an interface means what the file means; that the sums and the key are never written torn in a way that passes them (a file is checked, not made atomic); `file_chdir` is the process's, so the memo's operations run inside the copy (`<work>/app`) and the paths are absolute. Found on the way, not fixed here (bats-lang/bats#305): `build/.bats_toolchain` is trusted across processes whatever `patsopt` now is (an edit in place is not seen by the stamp until the file is removed), which the stamp of #273 was to prevent.
