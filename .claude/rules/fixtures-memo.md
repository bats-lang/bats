# The fixtures' memo

**The fixtures' memo** (bats-lang/bats#267, item 4b; `src/fixtures.bats`, `tests/fixtures/check.sh`). A fixture whose result was kept is not run again when everything patsopt reads for it is as it was. The output keeps quire's shape, `ok   accept/<name> (N s)`, and a fixture served from the memo says `ok   accept/<name> (0 s) [memo]` (the marker after the seconds, so a reader that matches `ok   <member> (N s)` still does), and the last line gains ` (K from the memo)` only when K is more than 0. **A hit stands in for patsopt's answer on the spliced module and for nothing else**: for every fixture, after the snippet is put in and before the memo is asked, `validate_clean` (`src/lock.bats`, the body of `validate_project` without its report: the lexer's rules and the call cycles of every `.bats` of the package, which have no patsopt in them) runs on the project as the check would see it, and a project it refuses is not looked up (the fixture runs, and `bats check` says why). The first version of this memo asked first, so a cycle through another module's `implement`, made after an entry was kept, was served as a pass (the review of bats#303); `tests/fixtures/check.sh` ("a hit stands in for patsopt's answer") plays it. The price was the validation itself: it lexed every `.bats` file of the project and its dependencies twice for each fixture (on quire about 100 s of a 115 to 145 s warm check, measured on a loaded machine). It now reads what `validate_project` already judged (`src/validated.bats`, bats#296): the base check of the run leaves a record for each file that passed under `build/.bats_valid` of the copy, each keyed by the sha256 of the file and of the context (bats's inputs, the packages installed, whether the package is unsafe), and `validate_clean` is the same function with the same records, so a fixture lexes only what its snippet changed (the one module) and the call cycles of `./src` again (the files of the package that an earlier fixture of the run scanned with the same bytes are not lexed again: recursion.md) (that record's key holds every source file's path and sha256, so a cycle made by a later change in another module changes the key and is looked for: the case in `tests/fixtures/check.sh`). The dependencies' files and the dependencies' cycles are not lexed again. Nothing reads a time. The check memo of #298 has no such hole: `validate_project` runs in `bats.bats` before `do_check`, and its memo sits inside `do_check`, so the same project is refused by `bats check` with every module warm (a case of the same test). *Key* (sha256 of the text of eight lines, the first line only the format): the module's path from the project's root, the sha256 of `before`, of `snippet.bats`, of the module with the snippet in, of `bats.toml`, of `bats.lock`, and of `build/.bats_stamp` (the bats, patsopt, C compiler, flags and mark: the toolchain). No path of a checkout is in it (a project at another path, a memo copied elsewhere, hit). The `expect` is not in it. *Entry*: two files, `<memo>/<2 hex>/<key>.key` and `<key>.res`. The `.key` is a `bats-memo 1` text of the check memo's own kind (`closure_key_write`, `closure_key_equal` in `src/cache.bats`, the code that `memo_fresh` uses): the sorted names of every `.sats`/`.hats` of `build/` and `.bats` of `src` and `bats_modules` (a module added or removed: what patsopt might read instead of a file), the files patsopt reads for the module (the list `patsopt --depgen` makes, followed to the end, less the module's own `.dats` and `.sats`: the module with the snippet in stands for them in the key), and for each its size and sha256, a `.sats` digested as an interface (newline runs collapsed) and any other file as it is. Nothing reads a time: a file is the same when its digest is. The `.res` is `bats-fixture-result 2`, the key, `pass` or `log`, the sha256 of the `.key`'s bytes, the log (none for a pass) and, last, the sha256 of every byte before it. *Lookup*: an entry is served when its `.res` is whole (format, key, kind: an accept is served only a `pass`, a reject only a `log`, closure digest and sum right) and its `.key` is the one the `.res` names and `closure_key_equal` finds every file as it says; anything else (absent, empty, torn, garbled, foreign, of another format) is a miss and the fixture runs. *Writes* are plain: the file package has no rename, so no file is written beside its place and moved. What takes the place of the rename is that a reader trusts nothing it has not checked: a torn `.res` fails its sum, a torn `.key` fails the `.res`'s digest of it, two writers of one key write the same bytes (the key says what is in them), and a run killed while it checks has written nothing (the entry is the last thing a run does). A reader that meets a `.key` of one writer and a `.res` of another finds them equal or a miss. There is no liveness check (no `kill -0`, no time). A directory is a memo only when it holds the mark `.bats-fixtures-memo`, which the first store makes in an empty directory (or one with only a mark), and a subdirectory only when it holds `.memo-dir`; bats neither reads from nor writes to another (a mistyped `--memo` is not filled, nor pruned). *What is kept* (after a run, never before): an accept that passed, as `pass`; a reject whose check failed the ordinary way (status 1 and a line `...: error(N): ...` of patsopt's, a log of at most 262144 bytes as kept), as `log`, the log as bats printed it with the work directory's path written `/app/` and the lines that vary with the machine dropped (`waiting for another bats`, the warning about an ATS2 bats did not install). A reject's entry holds the log, not a verdict: the expect is judged against it at every run, hit or not, by the same matcher, so a changed or wrong expect, or a fixed matcher, takes effect with no patsopt run. Never kept: an accept that fails, a reject that passes, a check that fails with no patsopt error (a refusal before patsopt, a status 124 or 125 of a cap, a signal), a fixture that could not be put in, a snippet that names `staload`, `dynload`, `load` or `include` as a word (a word is a run of identifier bytes, `is_word_byte`, which is the lexer's `is_ident_byte` and nothing more, so `load'` is the word `load`; not inside a longer name such as `Download`, bats#432) or `#use` or `#require` anywhere (it reads a file the module's list does not name; it is checked at every run), and a snippet that changed the module's interface (its `.sats` digest is not the base's: a dependent can fail on what it changed, and the closure of the module does not name the dependents; such a fixture is checked at every run, which is the cost of not recording them). *Where*: `--memo <dir>`, else `BATS_MEMO_DIR`, else `$XDG_CACHE_HOME/bats/fixtures`, else `$HOME/.cache/bats/fixtures` (ccache's default is `~/.ccache`, or `$XDG_CACHE_HOME/ccache` when it is set; Bazel's disk cache is opt in; `BATS_LOCK_DIR` here defaults to `~/.cache/bats`); the directories are made absolute when the run starts, since the memo is used from inside the copy. Sharing between checkouts and worktrees is the point and the key holds the toolchain, so it is sound; a CI job caches the directory alone (GitHub's cache is immutable per key: restore the newest `restore-keys` prefix, save under a new key when entries were added). *`--cold`* (or `BATS_COLD` set to anything but `0`) reads no memo and runs every fixture, writes the memo, and is an audit, a re-verification (the validation above is not left to it): when the memo had an entry that would have been served and the cold run says otherwise (an accept the entry says passes and now fails; a reject whose log, as kept, is not the cold run's) the fixture is `FAIL <member>: STALE MEMO: <why> (key <key>)`, the status is 1, the entry is replaced by the cold run's own result when that is one to keep, and else removed, so a key that missed an input shows as a red run (main's run is meant to be cold, as the check memo's). The base check and the fixture's check under `--cold` are bats's own incremental ones (only the memo is cold). *`--prune`* (not with `--only`, status 2) after the whole set has run removes the files of the memo that no fixture of the run used, one line `pruned <2 hex>/<name>` for each and `memo: pruned N files, kept M`; it touches only regular files named `<64 hex>.key` or `<64 hex>.res` in a two-hex-digit subdirectory that holds `.memo-dir`, in a marked memo, never through a link.

What is done in sh, and what is not proved. The memo is all in bats: the lookup, the store, the audit and the prune use the file package (`file_read`, `file_write`, `dir_read`, `file_chdir`, `file_mkdir`), the path package, the `sha256` package, `src/cache.bats`'s key and `src/lock.bats`'s `validate_clean`, and the command has no `sha256sum`, `shasum`, `find` or `kill` of its own. What is still `sh`, and is not the memo's: `splice_snippet` (`head`, `awk`, `tail`, `mv`: putting the snippet in a module), `run_check` (`cd app && bats check`, its output in a file, `date`), `restore_copy` and the copy of the project (`tar`, and a `find` that empties the copy), all from #297, as the rest of this command runs them; the memo adds none. Its one external program is `rm -f` of a file, through bats's own `remove_output` (an `exec` of `rm`, not `sh -c`, as the compiler's cache removes a stale output): the file and process packages have no unlink. Why those stay: the file package has no rename, unlink or copy, and the process package starts a program, so the copy of a tree and the removal of a file are the system's; the avenues that were open do not reach: `file_write` writes a whole file and cannot append or rename (the memo works around the missing rename with a checksum, above); the process package cannot give a child another directory other than by `sh` (hence `cd app`); `dir_read` lists a directory but names no file type, so the prune removes only files it names by a 64-digit key and `.key`/`.res`, from a subdirectory that holds a mark, and the refusal of a link is tested (`check.sh`, "--prune"). A small package change (rename and unlink in the file package, a `cp -R`) is the right place to remove this residue; no package was changed here. What is not proved, and is tested another way: that `patsopt --depgen`'s list (bats#298's) names every file a module's check reads; that the digest of a `.sats` as an interface means what the file means; that the sums and the key are never written torn in a way that passes them (a file is checked, not made atomic); `file_chdir` is the process's, so the memo's operations run inside the copy (`<work>/app`) and the paths are absolute. `tests/fixtures/check.sh` plays: a second run served wholly with no patsopt on a fixture, the key with no absolute path, the three ways to name the directory, an unrelated module changed (not run), a module that reads the module's interface changed in its body (not run), the module changed (run), a staloaded `.sats` changed to one of the same size (run), a module added, a changed snippet and `before`, a changed toolchain (bats-lang/bats#305, below), a changed or wrong expect (judged again, no patsopt), a stored log doctored (judged, and found stale by `--cold`), a memo that lies (found, dropped), a `.res` truncated, garbled, empty, foreign, of another format, of another closure, shortened or of another kind and a `.key` truncated, of another text or missing, failures that are never kept, a snippet that loads a file or changes an interface, a run killed in its check, four copies of the project over one memo for five rounds (some of them cold), `--prune` (a linked directory, a directory without the mark, a stray file, an orphan), and a hit that would hide a cycle through another module's `implement` (and the same cycle in `bats check`). Its mutation list, each a one-line edit with the case that kills it, is in the header of `tests/fixtures/check.sh`. Found on the way, not fixed here (bats-lang/bats#305): `build/.bats_toolchain` is trusted across processes whatever `patsopt` now is (an edit in place is not seen by the stamp until the file is removed), which the stamp of #273 was to prevent.
