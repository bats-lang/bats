# The lock and locked packages

With a `bats.lock`, `check`, `build`, `run` and `test` use exactly the versions it locks, transitive ones too (`locked_deps` in `src/lock.bats`). The Rust bats's `resolve_deps`, and this one until now, never read the lock: they fetched the newest version of each package `src/` uses directly, so a committed lock pinned nothing and a missing locked version went unnoticed. Now each locked package that `bats_modules` does not hold at its locked version (the `.bats-version` stamp `fetch` writes, or the package's `bats.toml` version) is fetched from the repository after its archive's sha256 is checked against the lock, replacing what was there; a locked version the repository lacks, an archive of another sha256, or no `--repository` to fetch from is an error. A lock that does not match the project is an error too, with a hint to relock: a package used but not locked, one locked but not used, or a locked version `bats.toml`'s constraints rule out. Newer versions in the repository are not an error; `bats lock --dry-run` still reports them as a stale lock. **A held copy is the locked archive, not only the locked version** (#321): `fetch` writes `bats_modules/<pkg>/.bats-version` as two lines, the version and the sha256 of the archive it unpacked, and the locked walk (`installed_locked`) takes a copy as installed only when that text is exactly what the lock's version and sha256 give. A mismatch (the lock's sha256 changed, a copy of another archive at the same version) goes to `install_locked`, which fetches and checks the new sha256 against the lock when there is a repository, else gives its error; a copy with no recorded sha256 (a stamp of an older bats, which wrote the version alone, or no stamp: a package unpacked by hand) is not the locked archive either and is fetched once, which costs one refetch per package after an upgrade. What is recorded is the archive's sha256, not the unpacked files': a copy edited in place after the fetch is not noticed (Cargo checks a crate's checksum against Cargo.lock when it downloads it and Go's go.sum at the download, not each unpacked file at each build; npm's integrity is checked at install), because hashing every installed file at every run is not cheap; a changed archive or lock is. The walk with no lock (`installed_at`) compares the stamp's first line, the version, only. The stamp is written last, and only when the unzip and the write both succeeded; otherwise `fetch` says the failed step as an error, removes the directory and answers false (every caller stops), so no stamp stands over a copy that is not the archive. The sha256 recorded is the one that was checked: `install_locked` hashes the archive once, against the lock, and hands that digest to `fetch`; with no lock nothing was checked, and `fetch` records the digest it reads of the archive just before the unzip. The stamp sits in `bats_modules`, which the validated and memo records already key on by listing and by file sha256, so they are unaffected. `tests/locked-deps` plays the lock's sha256 changed for an installed package (with and without a repository), restored, a stamp with no sha256, a missing stamp, another recorded sha256, a package not installed, and an `unzip` that fails (no stamp, no directory, an error, refetched next time). `bats lock` replaces what `bats_modules` holds of another version, so a relock reads each package's own `#use`s from the version it locks (`tests/locked-deps`). Without a lock, the newest version of each package `src/` uses is fetched, as before.
