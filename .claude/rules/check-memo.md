# The check memo

In check and test mode a module is not checked again when the files patsopt read for it are unchanged (bats#267, item 3; `src/cache.bats`, `tests/check-memo`). The record is the same `<C>.key` beside the C, in a text of its own: `bats-memo 1`, a `names` line (the sha256 of the sorted names of every `.sats` and `.hats` under `build/`, the stashes of other marks left out), the module's closure (one path a line, the list `patsopt --depgen` gives followed to the end, which is the `.dats`, every `.sats` and `.hats` its staloads and includes reach, and a staloaded dependency's `.dats`), a `--` line, the size of each of those files in order and of `build/.bats_stamp`, and then their sha256s in order and the stamp's. The list is the key's own, read back from it, so `patsopt --depgen` runs only when patsopt ran and passed (bats#253 measured 0.4 s a module), and a later check only rehashes the files named. The first module of a pass that needs a list fills a graph (`build/.bats_graph`, a line `<file> <TAB> <the files it names>`) with one `--depgen` of every `.dats` and `.sats` of `build/src` and `build/bats_modules`, and the walk to the end is done on that graph, so a file that many modules reach is read by patsopt once; a file the graph lacks is asked for, a level at a time, and added. The graph is removed whenever the names are listed again (below), so it is never older than the files it was made from; its answers were compared with the level-by-level walk's on each module of bats's own project (same list for every one). It is written after patsopt and `check_emitted_flaws` passed, to `<C>.key.new` and renamed into place, so a reader sees a whole key or none, and removed before patsopt runs (a failed or killed run leaves none; a module that failed is never recorded and is checked again at the next run, whatever its bytes). Fresh means the C is there and the text made again from the files as they are now begins with, and then equals, the key's: the sizes are compared first, then the hashes. A key that is missing, short, garbled, of another format or with one number changed is not equal, so the module is checked. No time is read anywhere in it. `bats check --cold`, or `BATS_COLD` set to anything but `0`, ignores every key and writes them again, in a build too since bats#323 (main's run is meant to use it; quire's gets the same by not restoring `build/`, it sets neither). `-v` prints `  = <C> (unchanged)` for a module skipped. The stamp is not repeated in the key's rule: `build/.bats_stamp` is judged first and drops a `build/` that differs, and its size and sha256 are the key's last line of each part, so the toolchain, the compiler, the flags and this bats are in the key through it. A build uses the same key and the same code (`memo_fresh`, `memo_record`, bats#323), with one more line in the list, `build/.sats_changed`, so a changed `.sats` still rebuilds every C there, since a C that is shipped is not to be trusted to a closure bats cannot prove complete; a check and a test do not read it. The graph of `--depgen` answers is made by the first module of a build as it is of a check, and a module with no key (its `--depgen` failed, the shell that appends the `build/.sats_changed` line to the key failed (bats#333: a key is written whole or not at all, never without that line), or the key would reach 524288 bytes) is made again at every build, and `-v` says so (`  ! no key for <C> (depgen failed)`, `(appending build/.sats_changed failed)`, or the size one). The other places a shell's status is not read are safe: the move of `<C>.key.new` to `<C>.key` (the old key was removed before patsopt ran, so a failed move leaves no key), the store of a C in the shared cache (copied beside its place and renamed, so an entry is whole or absent, and a hit is checked as patsopt's output is), and the records of `build/.bats_valid` (a record is trusted only when its key equals the one the file gives now, so a record not written, or cut short, is judged again). `--cold` and `BATS_COLD` make a build ignore the keys too (and write them again), not only a check: quire's main run builds cold by not restoring `build/`, it does not set `BATS_COLD`. What comparable tools do: ccache's direct mode and depend mode hash the content of every header a compile read (the manifest of includes) and fall back to the preprocessor when one differs, sccache keys on the preprocessed output, and Bazel on declared inputs with the toolchain; none takes a time or only the translation unit's own file.

Three things are not obvious. (1) A `.sats` is digested as its interface, not its bytes: its length and sha256 are those of its text with each run of line feeds taken as one, tagged `C`, so a declaration added before a module's `#pub` ones (a static fixture's snippet) moves the `.sats` and changes no module that staloads it, as `sats_moved` has it for the `.sats_changed` stamp; a `.sats` with a line feed in a string or char literal, a `%{` or an open comment is digested as it is, tagged `R`, the same lexical scan `sats_moved` uses (`newlines_between_tokens`). The "size" of a `.sats` is the length of that text, so it is still a negative only. (2) A module's closure is what patsopt reads, so a body-only change to a staloaded dependency's `.dats` checks the modules that staload that `.dats` again (a bin that `#use`s a dependency does), which the `.sats_changed` stamp did not and which is right: patsopt reads a staloaded `.dats` (templates). (3) A file that patsopt would have read had it existed, a `.sats` of the same name earlier on `-IATS build -IATS build/src -IATS build/bats_modules`, is in no module's list, so the `names` line holds the name of every `.sats` and `.hats` of `build/`: a module added or removed (or a dependency, whose `.sats` appear in `build/bats_modules`) checks every module again. That is conservative on purpose. A project with several bins emits all the bins of a pass before it checks any (`emit_bins`, bats#353), so the first bin's key names the same `.sats` the next listing does and a cold check settles in one check (`tests/names-graph`). The digests of the files many modules share are kept for a run too: a `.sats` and every file under `build/bats_modules` (a staloaded dependency's `.dats` is several hundred kilobytes, and its sha256 in a debug bats is slow) are digested once, into one table in the memory of the process (bats#311; they were a file each in `build/.bats_dg`, about 5,000 reads and an open each in an unchanged check of quire's size), and looked up by the other modules; a module's own `.dats` is hashed where it is needed. The table is an array of 1 MiB of entries (the path, a line feed, the size line, the hash line) and an array of 16384 ints, an open-addressing index by a hash of the path (`digest_entry`, `dg_find`, `dg_insert` in `src/helpers.bats`); an entry is found by comparing the whole path, a table that is full keeps no more (those files are digested each time), and an entry that does not have the shape of a size line and a hash line is not kept. The table is emptied (`digests_forget`) wherever the names are listed again, in `names_digest`, so an entry never outlives a run (it is in one process's memory) or the files it digests within it; `bats fixtures` empties it before it reads a closure, since the checks it runs are processes of their own that move the files. Nothing reads or writes `build/.bats_dg` any more, and a listing removes one an older bats left. What is proved: every read and write of the two arrays by its index, and the termination of every loop; what is not: a slot is an int read back from memory, which has no index in its type (the index is a plain int array, not array's `iarr`), so `slot_read` takes a value outside the bytes written to be an empty slot, which is a miss and digests the file again. The listing (`build/.bats_names`) is made once after anything that adds, removes or moves such a file (`names_set_fresh(false)`: a `.sats` emitted, which is `touch_sats_stamp`, `build/` swapped in by `cache_swap`, the orphans pruned) and its sha256 is read at each lookup; before this it was a `find` and a sort for each module, twice, which made a no-change check 9 to 12 s slower than main's.

What is not proved, and is checked another way: that `patsopt --depgen` lists every file a module's check reads (it is the walk `BATS_CACHE_DIR`'s key has used since bats#250; its limits are patsopt's, and a `staload` of a file by a name built from the environment is not seen); that the squeezed text means what the original does (the lexical scan is a function of the bytes and is tested, `tests/sats-moved`, not proved); that renaming into place is atomic on the file system in use (POSIX says it is on one file system; a `build/` on a file system that is not is not covered); and that `names` is read before patsopt runs and the closure after, with nothing between them that changes a `.sats` (bats holds the project's lock, so only bats itself does, and all the emissions are done by then). `--cold` on main is the detector for a closure that missed a file, as it is for `build/` in quire. `patsopt --depgen` is started by `sh` in every case and is held to `BATS_PATSOPT_TIMEOUT_S` and `BATS_PATSOPT_MEM_MB` by the same wrapper `patsopt_only` uses (time: status 124, memory: 125, the same error naming the module; a depgen that hangs once hung a `check` past the cap); `tests/patsopt-cap` plays a hanging `--depgen` and leaves depgen out of its count of who started patsopt, since sh starts it whether a cap is set or not. A key that would reach 524288 bytes (the most bats writes) is not written, and `-v` says so; the module is then checked again at each run. The root package of a library (`build/src/lib.dats`) was checked at every `bats check` whatever its inputs; it is skipped now by the same key. Measured (one machine, 4 cores, one `bats -v check` at a time, main's bats at cb6ab0e against this one; seconds and patsopt runs, then `--depgen` starts for this one) on bats's own project of 33 modules and on a project of six modules and two bins, a native and a wasm one, over arith, array, builder, css, str, widget, promise, result, json, bridge and dom. Own project: cold 84 s, 33 runs against 89 s, 33, 2 starts; no change 35.3 s against 37.6 s; a leaf module's body changed 36.7 s, 2 runs against 39.3 s, 2, 1 start; a leaf module's `.sats` changed 81.9 s, 33 runs against 42.3 s, 4, 2 starts. The other project: cold 126 s, 110 runs against 141 s, 110, 4 starts; no change 33.4 s against 39.5 s; body 34.2 s, 2 against 41.8 s, 2, 2 starts; `.sats` 143.5 s, 110 against 42.8 s, 4, 3 starts. The first version of this memo started `--depgen` 86 times on a cold check of the own project and 300 on the other (one patsopt per level of each module's closure) and took 104 s and 183 s. The memo is not at parity where nothing changed or only a body did: 2 s (own project) and 6 s (the other) slower, which is the digest of the files a module's closure holds that main never read, taken once for a pass: a staloaded dependency's `.dats` (bridge's and dom's are the large ones) and the `.sats`, whose sha256 in a debug bats runs at a few hundred kilobytes a second (stack samples of the no-change check are mostly the sha256 rounds), against main's one `.dats` for each module. Hashing less would mean trusting a `.dats.src` sidecar for a file bats wrote (a kill between the two writes leaves a `.src` that is not the `.dats`'s), which is not done; a release bats would be faster. The roughly 20 s that bats spends before its first child process in every check (bats#296) is the same in both and is not touched. The neighbouring tests changed with this: `tests/build-content-keys` no longer expects a changed `.sats` or a stamp ahead to check every module (a check does not read `.sats_changed`; the build part of the test does), and expects a changed body of a dependency to check the bins that staload its `.dats`.

Neither an object nor a key of an object is kept here: the shared cache holds patsopt's C, which
names the project's files relative to the project, and this memo's closure lists names under
`build/`; an object's key is in build-freshness.md.
