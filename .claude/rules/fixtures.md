# bats fixtures

`bats fixtures <dir> [--only <member>]... [--cold] [--work <dir>] [--memo <dir>] [--prune] [--repository <dir>]` (bats-lang/bats#267, item 4: quire's static-test runner, `tests/static/run.sh` and `expect.py`, folded into bats; `src/fixtures.bats`, `tests/fixtures`) runs a directory of fixtures against a copy of the project (the current directory). A fixture is `<dir>/accept/<name>/` or `<dir>/reject/<name>/` with `file` (the project's module, from its root), `before` (a line of it), `snippet.bats` and, for a reject, `expect`; the snippet is put into the module followed by one blank line, before the first line that is exactly `before` (no such line is a failure of the fixture), because what a fixture tests is private to its module. The project is copied to `<work>/app` (everything but `build`, `dist`, `.git`, `node_modules` and `test-results`) and checked whole first with `bats check` (the program as it was run; the fixtures mean nothing if it does not check, so the run fails and no fixture runs), its `build/` kept in `<work>/build-checked` and put back, with the module, after each fixture: each starts from the project as the check left it, so only its module is checked again (with the freshness and the stamp bats already has: nothing is re-implemented here). `--work` keeps the directory (CI restores its `app/build` between runs); without it a `mktemp -d` one is made and removed. An accept passes when `bats check` passes. A reject must fail it exactly as its `expect` says (`expect.py`'s rules, ported to bats): `function <name>`, `line <n>`, then patsopt's error as it says it (its message after `error(N): ` and the lines it adds to it, up to patsopt's summary, bats's own `error:` lines, `exit(ATS)`, a blank line); an expect that is not that form (two lines, another word, a line that is no number, empty, absent) is a failure of the fixture, never a pass; the declaration (`fn`, `fun`, `fnx`, `prfn`, `prfun`, `implement`, `val`, `var`, `and`, then `{...}` groups, then a name) enclosing line `n` of the snippet must be `<name>`; there must be at least one patsopt error, each in the module `file` (its path ends with `/` and the module) and at snippet line `n`; and their text, line for line, must be the expect's, with only patsopt's variable numbers compared as `_` (`S2EVar(N->`, `$N(` and `S2Evar(name(N))`: not the constants, not a number of another form). A substring that another error could also hold is not enough. The output is one line per fixture as run.sh printed it, `ok   accept/<name> (N s)` or `FAIL reject/<name>: rejected, but not as its expect says: <why>` (followed by the patsopt lines that name an error), then `fixtures: N ok, M failed`; the status is 1 when anything failed, 2 for a usage error (an unknown option, no directory or two, an `--only` that names no fixture: a member is `accept/<name>` or `reject/<name>`). `--only` is repeatable. `--cold`, `--memo` and `--prune` are the memo's (fixtures-memo.md). What the system does that bats does not (copying the tree, putting the lines of the snippet in, running `bats check` with its output in a file, `date`, `mktemp`) is `sh`, `tar`, `head`, `awk` and `tail` run by the process package, as `src/cache.bats` runs `sh`; which line, and what the output means, are decided in bats. The program run for the checks is the one that was run (`argv[0]`, resolved to a path when it has a `/`, else through the PATH); `GIT_DIR` is taken from the project's repository for a module that staloads `_bats_facts`. What the types prove, and what is a branch on the data instead of a proof: every read of a text is proved in range (a text's length is `tlen`, `[n:nat | n <= 524288]`, from `read_text`, whose answer is `[k:int | ~1 <= k; k <= 524288]`: the file's length or ~1; `text_len` maps the ~1, which the caller has already said as a failed read, to an empty text), `text_has` and `step_text` check that the text lies inside the buffer before comparing and answer a position the types bound, `step_digits`, `header_parse` (a position of the line it returns is proved between the line's start and the text's end, by the chain of its 14 steps, each in the success branch of the one before), `trim_end`, `trail_blank`, `variable_end` and the rest return positions or lengths indexed by the bounds they keep, so no clamp of a length or a position remains (the `clamp_len`, `put_between` and `put_text` of the first version are gone). What is still a branch, and no proof: the orderings that depend on the text read (`ns <= e1`, `ls <= e2`: whether the expect's first line is longer than "function "; `ne >= ns` in `decl_is`; `r > p` and `r <= len` in `variable_end`, where the end of a match is computed from bytes through plain ints and `g1ofg0`; the `p15 <= b` end of a header), each of which decides the answer (not a header, not that function, no variable) and none of which a proof could replace without the text being known; and the offsets of the settings buffer (`g1ofg0` of a builder's length). Differences from `expect.py` (Python), in the direction of failing a fixture, except two cases where this accepts what Python does not: an expect that spells literally a message containing `\x0c`, U+2028 or a line of NBSP alone, as the log has it, is ok here and fails in Python (which splits the log there), and a `file` padded with spaces or other whitespace is stripped here (as `expect.py` strips it) while run.sh's raw `cat` of it would not find the module: an expect with CRLF line ends fails here (its lines keep a `\r`) and passes in Python only if the snippet's error does too; `int()` of the line accepts `+1` and `1_0` in Python and is digits only here (a `+` or `_` is a malformed expect); whitespace (`strip`, the space after the function) is ASCII only (space, `\t`, `\n`, `\v`, `\f`, `\r`, `\x1c` to `\x1f`), so NBSP, `\x85`, U+2028 and U+2029, which Python's `str.strip` and `splitlines` also take, are not; a log is broken at `\r\n`, `\r` and `\n` as `splitlines` does for those, but not at `\x0b`, `\x0c`, `\x1c` to `\x1e` (control characters patsopt does not print). A directory with no fixture in it (not there, empty, or only empty `accept` and `reject`) is a usage error (status 2), so a mistyped path in CI fails. The work directory is excluded from the copy of the project when it is inside it (`--work ./w`), and the check's log and seconds are removed before each fixture, so a snippet that could not be put in is a failure of that fixture, never judged against the last one's log. The texts are at most 524288 bytes each (a log, an expect, a snippet), the module at most what an arena holds. `bats fixtures` is read before bats's own arguments, as `with-env` is. Python's `splitlines` breaks a log at `\r` too, and so does the matcher (`\r\n` as one); `str.strip` is ASCII whitespace here. Tests: `tests/fixtures`.

**Paths and the arguments of the children are as big as their text** (bats-lang/bats#357, a piece of #327: `into_arr` as in the checker). Every path of the work directory, the memo and the app is built with `path_into` (the text and a NUL, in the builder's own array) and opened, tested, hashed, written, removed, listed, read, made and entered at its own length (`file_exists_m`, `put_file_sha256_m`, `write_file_from_builder_m`, `remove_output_m`, `dir_read_m`, `read_whole_m`; `mkdir_arr` and `chdir_path` split the borrow to the path's length, because helpers.bats has no `file_mkdir_m` or `file_chdir_m`); the arguments of a child are `arg_of` (the builder's own array, where `mk_arg` makes 524288 bytes: an `arg_entry` is of any size since process 2026.10.19); `memo_clear` removes a fixture's ten files with one `rm -f`, not ten spawns. What still makes 524288 bytes, and why: (1) the program of `sh` and `rm` (`str_to_path_arr`: `run_cmd`, in helpers.bats, takes a borrow of 524288, 2 or 3 a fixture); (2) the text buffers (`file`, `before`, `snippet.bats`, `expect`, the log, the memo's `.res`, `.key` and bookkeeping files, about 20 of the 27 a fixture that are left, measured on quire) and the key, memo and settings buffers: the text protocol of this file (`byte_at`, `text_has`, `line_end`, `header_parse` and about 300 signatures) is typed on an array of 524288 and the length `tlen`, the documented limit of a text, so moving them is generalising that protocol, not a call; (3) the two buffers `closure_key_write` (cache.bats) takes.
