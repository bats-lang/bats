# bats fixtures

`bats fixtures <dir> [--only <member>]... [--bless] [--cold] [--work <dir>] [--memo <dir>] [--prune] [--repository <dir>] [--list-affected <path>...]` (bats-lang/bats#267, item 4: quire's static-test runner, `tests/static/run.sh` and `expect.py`, folded into bats; `src/fixtures.bats`, `tests/fixtures`) runs a directory of fixtures against a copy of the project (the current directory). What the types prove, and what is a branch on the data instead of a proof: every read of a text is proved in range (a text is an array of its bytes and one more, with its length `n < m` indexed by the array's size, from `read_text`, which answers the array, the length and whether the file could be read: a file that could not, or holds over 524288 bytes, is an empty text of one byte, and the caller has said so; every function of the text protocol takes the array's size as an index of its own (`bv_cap`), so a text, a path, a key and the settings buffer are each as big as what they hold, bats#368), `text_has` and `step_text` check that the text lies inside the buffer before comparing and answer a position the types bound, `step_digits`, `header_parse` (a position of the line it returns is proved between the line's start and the text's end, by the chain of its 14 steps, each in the success branch of the one before), `trim_end`, `trail_blank`, `variable_end` and the rest return positions or lengths indexed by the bounds they keep, so no clamp of a length or a position remains (the `clamp_len`, `put_between` and `put_text` of the first version are gone). What is still a branch, and no proof: the orderings that depend on the text read (`ns <= e1`, `ls <= e2`: whether the expect's first line is longer than "function "; `ne >= ns` in `decl_is`; `r > p` and `r <= len` in `variable_end`, where the end of a match is computed from bytes through plain ints and `g1ofg0`; the `p15 <= b` end of a header), each of which decides the answer (not a header, not that function, no variable) and none of which a proof could replace without the text being known; and the offsets of the settings buffer (`g1ofg0` of a builder's length). A directory with no fixture in it is a usage error (status 2), so a mistyped path in CI fails. Tests: `tests/fixtures`.

**`--bless` (bats-lang/bats#522; `bless_in`, `bless_member`, `tests/fixtures/bless.sh`).** `bats fixtures <dir> --bless [--only <member>]...` writes each reject fixture's `expect` from the error patsopt gave, the variable numbers written as `_`, so a renumbering by patsopt never changes the expect and the diff shows only a change in what the error says. It is refused, and nothing is written for it, when the check passed. Nothing is written without the matcher agreeing, so an expect written by `--bless` passes the next run without it by construction. An expect the fixture already has that passes the matcher against the log is left as it is, so a bless rewrites only what no longer passes, and a second bless changes nothing. The new expects are meant to be read: the written files are a diff in the pull request, as the `.stderr` files `--bless` of rustc's UI tests, the snapshots of `jest -u` and `cargo insta`'s `.snap` files and Go's `-update` golden files are; `--bless` is run after the last edit of the module, because an expect blessed from an error that is itself wrong is a record of the wrong error, which only that reading sees. Research (what the comparable tools do against a rubber stamp): rustc's compiletest `--bless` rewrites the files and the reviewer reads them in the diff; it normalizes what varies (paths as `$DIR`, line numbers as `LL`) so the diff is the message's change, which `_` is here; Jest's `-u` rewrites every obsolete or failing snapshot, and `--ci` (the default under CI) refuses to write a new one, so a run in CI cannot create its own expectation: here `--bless` is an explicit option that CI does not pass, and a plain run never writes; insta writes `.snap.new` files and only `cargo insta review/accept` promotes them, an explicit step with a pending file to read, and `INSTA_UPDATE=no` in CI: the bats equivalent of the pending step is the diff of the PR, since the files are in the repository; Go's golden-file idiom (`-update` flag in the test) rewrites the files and relies on `git diff`. None of them refuses on content, which is where bats goes further: a bless of an error with the wrong shape (no error, an error in another module, errors at two lines, no declaration) is refused, and the written expect is judged by the matcher before it is written.

**`among` (bats-lang/bats#573; `unmatched_scan`, `unmatched_answer`, `tests/fixtures/check.sh`, keyword: among).** A reject's expect may say, instead of the whole error, that one constructor is among the unmatched ones of a nonexhaustive match: after `function <name>` and `line <n>` the rest is exactly the two lines `pattern match is nonexhaustive:` and `among <Constructor>`, the constructor written as patsopt prints it (`RoleSecondHighlight()`). Why this form: patsopt names each unmatched constructor in an error of its own at the same place (a datatype of `A | B | C` matched by `A()` gives two errors, `pattern match is nonexhaustive:` / `B()` and the same header / `C()`), so the line-for-line expect lists one block for each, and adding a constructor to the datatype breaks every such expect; `among` keeps the header (so it applies to this error alone) and says the one constructor that matters. The line-for-line form is unchanged (additive).

**`--list-affected` (bats-lang/bats#570; `list_member`, `own_changed`, `list_in_app`, `reads_changed`, `collect_changed`, `tests/fixtures/list.sh`, keyword: list-affected).** `bats fixtures <dir> --list-affected <path>...` prints, one `accept/<name>` or `reject/<name>` a line in the order of a run, every fixture a change to the paths reaches, and runs none of them: it is the reverse of the memo's `.key` (the exact form of Bazel's `rdeps`, Nx's task inputs and pytest-testmon's per-test file checksums), for a worker's local run to pick the fixtures a branch touched. it has no usable entry: it cannot be known, so it is listed (fail closed). `--changed-since <rev>` is not provided: `git diff --name-only <rev>` gives the paths.
