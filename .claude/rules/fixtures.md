# bats fixtures

`bats fixtures <dir> [--only <member>]... [--bless] [--cold] [--work <dir>] [--memo <dir>] [--prune] [--repository <dir>] [--list-affected <path>...]` (bats-lang/bats#267, item 4: quire's static-test runner, `tests/static/run.sh` and `expect.py`, folded into bats; `src/fixtures.bats`, `tests/fixtures`) runs a directory of fixtures against a copy of the project (the current directory). A fixture is `<dir>/accept/<name>/` or `<dir>/reject/<name>/` with `file` (the project's module, from its root), `before` (a line of it), `snippet.bats` and, for a reject, `expect`; the snippet is put into the module followed by one blank line, before the first line that is exactly `before` (no such line is a failure of the fixture), because what a fixture tests is private to its module. The project is copied to `<work>/app` (everything but `build`, `dist`, `.git`, `node_modules` and `test-results`) and checked whole first with `bats check` (the program as it was run; the fixtures mean nothing if it does not check, so the run fails and no fixture runs), its `build/` kept in `<work>/build-checked` and put back, with the module, after each fixture: each starts from the project as the check left it, so only its module is checked again (with the freshness and the stamp bats already has: nothing is re-implemented here). `--work` keeps the directory (CI restores its `app/build` between runs); without it a `mktemp -d` one is made and removed. An accept passes when `bats check` passes. A reject must fail it exactly as its `expect` says (`expect.py`'s rules, ported to bats): `function <name>`, `line <n>`, then patsopt's error as it says it (its message after `error(N): ` and the lines it adds to it, up to patsopt's summary, bats's own `error:` lines, `exit(ATS)`, a blank line); an expect that is not that form (two lines, another word, a line that is no number, empty, absent) is a failure of the fixture, never a pass; the declaration (`fn`, `fun`, `fnx`, `prfn`, `prfun`, `implement`, `val`, `var`, `and`, then `{...}` groups, then a name) enclosing line `n` of the snippet must be `<name>`; there must be at least one patsopt error, each in the module `file` (its path ends with `/` and the module) and at snippet line `n`; and their text, line for line, must be the expect's, with only patsopt's variable numbers compared as `_` (`S2EVar(N->`, `S2EVar(N)` (an unsolved variable with no arrow: its digits end at the `)`; patsopt prints `S2EVar(5245), S2EVar(5246)`, sha256's `sha1-one-shot-digest-as-sha256`), `$N(`, `S2Evar(name(N))` and `S2Eexi(name(N)`, the number of an existential's binder, and of each later binder of its list `S2Eexi(n(N), m(N); ...`, and the digits after a `$` in a name, `name$N$N(N)`, in it and in `S2Evar(...)` (bats#377; patsopt copies a variable it unpacks, sha256#46): the name is still compared, and so is every other term; not the constants, not a number of another form). A substring that another error could also hold is not enough. The output is one line per fixture as run.sh printed it, `ok   accept/<name> (N s)` or `FAIL reject/<name>: rejected, but not as its expect says: <why>` (followed by the patsopt lines that name an error), then `fixtures: N ok, M failed`; the status is 1 when anything failed, 2 for a usage error (an unknown option, no directory or two, an `--only` that names no fixture: a member is `accept/<name>` or `reject/<name>`). `--only` is repeatable. `--cold`, `--memo` and `--prune` are the memo's (fixtures-memo.md). What the system does that bats does not (copying the tree, putting the lines of the snippet in, running `bats check` with its output in a file, `date`, `mktemp`) is `sh`, `tar`, `head`, `awk` and `tail` run by the process package, as `src/cache.bats` runs `sh`; which line, and what the output means, are decided in bats. The program run for the checks is the one that was run (`argv[0]`, resolved to a path when it has a `/`, else through the PATH); `GIT_DIR` is taken from the project's repository for a module that staloads `_bats_facts`. What the types prove, and what is a branch on the data instead of a proof: every read of a text is proved in range (a text is an array of its bytes and one more, with its length `n < m` indexed by the array's size, from `read_text`, which answers the array, the length and whether the file could be read: a file that could not, or holds over 524288 bytes, is an empty text of one byte, and the caller has said so; every function of the text protocol takes the array's size as an index of its own (`bv_cap`), so a text, a path, a key and the settings buffer are each as big as what they hold, bats#368), `text_has` and `step_text` check that the text lies inside the buffer before comparing and answer a position the types bound, `step_digits`, `header_parse` (a position of the line it returns is proved between the line's start and the text's end, by the chain of its 14 steps, each in the success branch of the one before), `trim_end`, `trail_blank`, `variable_end` and the rest return positions or lengths indexed by the bounds they keep, so no clamp of a length or a position remains (the `clamp_len`, `put_between` and `put_text` of the first version are gone). What is still a branch, and no proof: the orderings that depend on the text read (`ns <= e1`, `ls <= e2`: whether the expect's first line is longer than "function "; `ne >= ns` in `decl_is`; `r > p` and `r <= len` in `variable_end`, where the end of a match is computed from bytes through plain ints and `g1ofg0`; the `p15 <= b` end of a header), each of which decides the answer (not a header, not that function, no variable) and none of which a proof could replace without the text being known; and the offsets of the settings buffer (`g1ofg0` of a builder's length). Differences from `expect.py` (Python), in the direction of failing a fixture, except two cases where this accepts what Python does not: an expect that spells literally a message containing `\x0c`, U+2028 or a line of NBSP alone, as the log has it, is ok here and fails in Python (which splits the log there), and a `file` padded with spaces or other whitespace is stripped here (as `expect.py` strips it) while run.sh's raw `cat` of it would not find the module: an expect with CRLF line ends fails here (its lines keep a `\r`) and passes in Python only if the snippet's error does too; `int()` of the line accepts `+1` and `1_0` in Python and is digits only here (a `+` or `_` is a malformed expect); whitespace (`strip`, the space after the function) is ASCII only (space, `\t`, `\n`, `\v`, `\f`, `\r`, `\x1c` to `\x1f`), so NBSP, `\x85`, U+2028 and U+2029, which Python's `str.strip` and `splitlines` also take, are not; a log is broken at `\r\n`, `\r` and `\n` as `splitlines` does for those, but not at `\x0b`, `\x0c`, `\x1c` to `\x1e` (control characters patsopt does not print). A directory with no fixture in it (not there, empty, or only empty `accept` and `reject`) is a usage error (status 2), so a mistyped path in CI fails. The work directory is excluded from the copy of the project when it is inside it (`--work ./w`), and the check's log and seconds are removed before each fixture, so a snippet that could not be put in is a failure of that fixture, never judged against the last one's log. The texts are at most 524288 bytes each (a log, an expect, a snippet), the module at most what an arena holds. `bats fixtures` is read before bats's own arguments, as `with-env` is. Python's `splitlines` breaks a log at `\r` too, and so does the matcher (`\r\n` as one); `str.strip` is ASCII whitespace here. Tests: `tests/fixtures`.

**`--bless` (bats-lang/bats#522; `bless_in`, `bless_member`, `tests/fixtures/bless.sh`).** `bats fixtures <dir> --bless [--only <member>]...` writes each reject fixture's `expect` from the error patsopt gave, in the form above, and prints one line per reject, `wrote reject/<name> (N s)` or `left  reject/<name> (N s)` (the `[memo]` marker as in a verifying run), then `bless: W written, L left as they were` before `fixtures: N ok, M failed`. The expect is `function <the declaration of the snippet at the line of the first error>`, `line <n>` (the snippet line of the first patsopt error) and the text of the errors as the matcher compares it: the variable numbers written as `_` (`S2EVar(_->`, `S2EVar(_)`, `$_(`, `S2Evar(n(_))`, `S2Eexi(n(_), m(_);`, `name$_$_`), so a renumbering by patsopt never changes the expect and the diff shows only a change in what the error says. It is refused, the fixture is `FAIL reject/<name>: not blessed: <why>` and nothing is written for it, when the check passed (`it type-checks, so there is no error to write`), the log has no patsopt error (`no error of patsopt's`: bats refused the snippet first), an error is not in the module `file` (`an error is in <path>, not <module>`), the errors are not all at the line of the first (`an error is at line N of its snippet, not M`) or that line is in no declaration. Nothing is written without the matcher agreeing: the expect `bless_in` made is judged by `judge` against the same log, and a mismatch is `the expect it would write does not pass`, so an expect written by `--bless` passes the next run without it by construction (`tests/fixtures/bless.sh` plays each kind: a function that is not the first, a line other than 1, several error lines, every kind of variable number, a fixture with no expect file). An expect the fixture already has that passes the matcher against the log is left as it is (`left`), raw numbers and all, so a bless rewrites only what no longer passes, and a second bless changes nothing. An accept fixture is run and judged as without `--bless` and never written to (a failing accept fails the run); `--only` blesses the members it names. The memo keeps the log and never the expect (the expect is not in its key), so a fixture served from the memo is blessed from the stored log and its old expect is never served; `--cold` reads no memo and writes it, `--prune` removes what no fixture of the run used and is a usage error with `--only`, both as fixtures-memo.md says. The new expects are meant to be read: the written files are a diff in the pull request, as the `.stderr` files `--bless` of rustc's UI tests, the snapshots of `jest -u` and `cargo insta`'s `.snap` files and Go's `-update` golden files are; `--bless` is run after the last edit of the module, because an expect blessed from an error that is itself wrong is a record of the wrong error, which only that reading sees. Research (what the comparable tools do against a rubber stamp): rustc's compiletest `--bless` rewrites the files and the reviewer reads them in the diff; it normalizes what varies (paths as `$DIR`, line numbers as `LL`) so the diff is the message's change, which `_` is here; Jest's `-u` rewrites every obsolete or failing snapshot, and `--ci` (the default under CI) refuses to write a new one, so a run in CI cannot create its own expectation: here `--bless` is an explicit option that CI does not pass, and a plain run never writes; insta writes `.snap.new` files and only `cargo insta review/accept` promotes them, an explicit step with a pending file to read, and `INSTA_UPDATE=no` in CI: the bats equivalent of the pending step is the diff of the PR, since the files are in the repository; Go's golden-file idiom (`-update` flag in the test) rewrites the files and relies on `git diff`. None of them refuses on content, which is where bats goes further: a bless of an error with the wrong shape (no error, an error in another module, errors at two lines, no declaration) is refused, and the written expect is judged by the matcher before it is written.

**`among` (bats-lang/bats#573; `unmatched_scan`, `unmatched_answer`, `tests/fixtures/check.sh`, keyword: among).** A reject's expect may say, instead of the whole error, that one constructor is among the unmatched ones of a nonexhaustive match: after `function <name>` and `line <n>` the rest is exactly the two lines `pattern match is nonexhaustive:` and `among <Constructor>`, the constructor written as patsopt prints it (`RoleSecondHighlight()`). Why this form: patsopt names each unmatched constructor in an error of its own at the same place (a datatype of `A | B | C` matched by `A()` gives two errors, `pattern match is nonexhaustive:` / `B()` and the same header / `C()`), so the line-for-line expect lists one block for each, and adding a constructor to the datatype breaks every such expect; `among` keeps the header (so it applies to this error alone) and says the one constructor that matters. It passes when one of the errors is that constructor's block; the errors are read in order up to it, each must be of the form header plus one line, and whatever follows the match is not looked at (the Done-when of #573 says "whatever else is listed"). It fails when the scan reaches the end without the constructor (`its error does not leave <C> among the unmatched constructors; patsopt listed:` and the errors as patsopt gave them) and when an error read before the match is of another form (`its error is not the one expected:` and the errors). The answer is the datatype `unmatched_answer` (`UnmatchedFound`, `UnmatchedAbsent`, `UnmatchedNotList`), matched with `case+`. The line-for-line form is unchanged (additive): `check.sh` runs it on the same two-constructor match (`among-old-form`), beside `among-first` and `among-last` (pass), `among-absent` (the exact failure text), `among-none` (no constructor named) and `among-other-error`. `--bless` writes the full form and leaves an `among` expect that passes as it is.

**`--list-affected` (bats-lang/bats#570; `list_member`, `own_changed`, `list_in_app`, `reads_changed`, `collect_changed`, `tests/fixtures/list.sh`, keyword: list-affected).** `bats fixtures <dir> --list-affected <path>...` prints, one `accept/<name>` or `reject/<name>` a line in the order of a run, every fixture a change to the paths reaches, and runs none of them: it is the reverse of the memo's `.key` (the exact form of Bazel's `rdeps`, Nx's task inputs and pytest-testmon's per-test file checksums), for a worker's local run to pick the fixtures a branch touched. `<dir>` is given before the option, and the words after `--list-affected` up to the next option are the paths, as the project names them (`./` and the project's own absolute prefix are dropped; `..` is not resolved). A fixture is listed when (1) the module its snippet is put into (`file`) or one of its own files (`file`, `before`, `snippet.bats`, `expect`) is a path; (2) its memo entry, found by the key the run would ask for (the module with the snippet in, `bats.toml`, `bats.lock`, the toolchain stamp), records a file patsopt read that is a path, where a module `src/X.bats` stands for the `build/src/X.sats` patsopt reads; (3) it has no usable entry (no memo directory, no `.key` or `.res`, a `.key` that is not a `bats-memo 1` text, a snippet that could not be put in, a file that could not be read): it cannot be known, so it is listed (fail closed). Because the key holds the module and the lock, a changed module or lock has no entry and every fixture it reaches is listed by (3) as well as by (1). The project is copied and checked whole first, as a run does (its `--work` build is reused), and the snippet is put into the app's module for the key and the module put back, so the memo needs no index of its own and is not written to; a `--memo` that is not a memo lists every fixture. It is a usage error with `--bless` (in either order) and with `--prune`, status 2. Known: a path under `bats_modules` is matched only by its own spelling (the memo records what patsopt read there by its path); `--changed-since <rev>` is not provided: `git diff --name-only <rev>` gives the paths. `tests/fixtures/list.sh` plays: a module lists its fixture and no other, a module the fixture's module staloads lists it by the recorded reads, an unrelated path lists none, each of the four own files, `./` and absolute spellings, several paths, `--only`, no path, a fixture with no entry, a missing memo, nothing written, and the usage errors.
