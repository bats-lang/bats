# Build freshness

A build reuses what an earlier build produced when it is still fresh; the Rust bats rewrote every `.sats` and `.dats` on every build, so its cache (input mtime equal to the recorded one) reran patsopt on everything. A `.bats` is emitted again only when its bytes are not those its `.dats` was emitted from (their sha256, kept in `<dats>.src`; an mtime cannot tell, since a relocked dependency's files keep their archive's older mtimes, `tests/source-replaced`); its `.sats` is written only when its bytes change, and then `build/.sats_changed` is written. Nothing reads a time to decide what is fresh (bats#254: a build and its inputs are made in one whole second, a stash is moved with its mtimes, a file is touched or replaced with an old time; each gave a build that did the work again, or not at all). A module's C and its object each have a key beside them, `<C>.key` and `<object>.key`, written after the tool passed and removed before it runs: for a C the check memo's key (check-memo.md: the sizes and sha256s of the files patsopt read for the module, its `.dats` and every `.sats`, `.hats` and staloaded dependency `.dats` it reaches, and the names of the project's `.sats` and `.hats`), and in a build also `build/.sats_changed` (bats#323: a template body changed in a dependency's `.dats`, its `.sats` the same, is instantiated again in the C of every module that staloads that `.dats`, which the key of the module's own `.dats` and the stamp did not see, so a dependent's C and object kept the old body), for an object the sha256 of its C, and for a native object also a line naming its profile, debug or release (bats#320: the two profiles share `build/`, a native object's cc flags are the profile's, `-g -O0` or `-O2`, and a release object was reused by a debug build and the reverse), so a build of the other profile makes the object again; the C's key and a wasm object's name no profile, since patsopt's C is the same in both and the wasm cc flags are fixed (`-O2`, no `-g`), so a wasm object is kept across debug and release builds (the other flags, the target and the mode are in `build/.bats_stamp`, which drops a `build/` that differs). An output is fresh when it is there and its key equals the one its inputs give now; the sizes are compared first, and a different size is a changed file with nothing hashed. A key that is missing, short or garbled makes its output again. `build/.sats_changed` is written whenever an emitted `.sats` changes, with new bytes each time (the sha256 of what it held), so in a build a change to a `.sats` rebuilds every module's C, as before (a check and a test do not read it: see check-memo.md), and a body-only change rebuilds its own module and the modules that staload its `.dats` (a dependent of a library), no others (`tests/sats-change`, `tests/build-content-keys`). The same keys serve the dependencies under a namespace (bridge, dom), the extra modules of a dependency, the wasm objects, the binary's own module and the entry's object (the entry's C is made again by every build, and an object is made again only when that C differs). The cost: every no-change check reads and hashes each module's `.dats` and each C once; the tests are `tests/build-content-keys`, which plays the no-change runs after a cold one with no settling, every file of `build/` given a time in the future and long ago, a changed body of the same size, a changed `.sats`, and a garbled or missing key.
