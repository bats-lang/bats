# bats with-env

`bats with-env <env-file> <command> [args...]` (bats-lang/bats#277, a subcommand, the owner's ruling: bats has subcommands, not scripts) gives a shell that reads no profile (an agent's, a CI-like step) a machine's bats settings (`BATS_SLOTS`, `BATS_LOCK_DIR`, `BATS_CACHE_DIR`, `BATS_REPOSITORY`, and whatever else the machine sets, such as pwa's `PWA_TEST_SLOTS`): the file's variables are added to bats's environment (the file wins over the caller's) and the command is run with the arguments exactly as given and the standard streams shared; its exit status becomes bats's own. It is read as a dotenv file, not sourced by a shell (`src/with_env.bats`): `NAME=VALUE` or `export NAME=VALUE`, `#` comments, a value bare, in single quotes (literal) or in double quotes, `$NAME` and `${NAME}` taken from the caller's environment (so `PATH=/opt/bin:$PATH` works), a variable set twice has its last value, nothing else interpreted. It is read before bats's own arguments, so the command's own flags (`--help`, `--`) are its alone. Comparable tools: `env -S`, direnv, `dotenvx run` and `docker run --env-file` set the environment of one command from a file and run it; docker's and systemd's do not expand, dotenvx and Compose do. `tests/with-env` plays it.

Exact rules of the file and the command (all `tests/with-env/check.sh`):

* The file is at most 64 KiB (65536 bytes is read, 65537 is refused) and sets at most 1024 distinct variables. Which line is a variable's last is found in one pass over the file with a table of the names (a first version asked every line whether a later one overrode it: a 64 KiB file of comments took over a minute); the 1024 is because the process package's argument is an array of 512 KiB, so a variable costs about 130 KiB of memory and a tenth of a millisecond, and 7000 of them (all a 64 KiB file can name) took 1 GB and 3 seconds. 1024 is also far above any machine file's size: comparable tools set no count, so this is a bound bats needs and others do not. A file of 64 KiB of comments, or of one variable set on every line, takes no time.
* Nothing is cut short, and, beyond the caller's own environment, nothing is made that exec would refuse late (the kernel's total counts the environment bats inherits too: a caller with 14 variables of 120000 bytes makes exec fail with 126 "Argument list too long" for a file well within the 524287). A name inside `${...}` over 255 bytes, a variable of the caller's whose value is over 64 KiB, an entry (`NAME=VALUE`) over 131071 bytes, and entries that together take over 524287 bytes (each with the NUL after it) make the whole run a usage error, status 2, naming the variable of the file that was being made (for the total, the variables are counted from the last of the file backwards and the one named is the one that crossed the limit). The limits are checked as the entries grow (a value is not copied when it would not fit), so a file that cannot work fails at once: 1024 variables each with `$BIG` five times, BIG being 64 KiB, took 26 s and then failed in exec with "Argument list too long". Where the numbers come from, as separate facts: (1) **the process package**: `spawn_inherit_env_with` copies the extra entries into one builder of 524288 bytes, a NUL after each (`_build_from_list`), and answers E2BIG when they do not all fit, which is `sum(len + 1) <= 524287`; `spawn_child_with` would put a `BATS_SLOT_HELD=<path>` entry first when this process holds a machine slot, but with-env holds none (it runs before bats takes any), so the whole 524287 is the file's. 4 entries of 131071 bytes were a late "cannot run: Argument list too long" (126) before this was budgeted. (2) **Linux** refuses an exec whose single argument or environment string is over MAX_ARG_STRLEN, 32 pages, 131072 bytes with the NUL (include/uapi/linux/binfmts.h; E2BIG), so 131071 is the kernel's own bound on one entry; and whose strings together are over a quarter of the stack limit (8 MiB by default, so 2 MiB, at most 6 MiB since 4.13; glibc's ARG_MAX says the same, at least 128 KiB), counting the arguments and the inherited environment too (mina86.com/2021/the-real-arg-max-part-2, kernel bug 10095, the LKML thread on raising MAX_ARG_STRLEN to 6M, which I could not find merged). (3) **macOS** has ARG_MAX of 1 MiB for arguments and environment together (`sysctl kern.argmax` is 1048576), so the package's 512 KiB leaves the rest to the caller's environment there. Docker (`--env-file`), Compose, dotenvx and systemd's EnvironmentFile document no limit on the number or size of the variables in a file that I could find (searched; Sitecore's Compose setup asks for 30,000 bytes a variable, which is its own); they pass the variables to the runtime and the kernel refuses. A value is read into 65537 bytes, hence the 64 KiB per expanded variable. Only the effective (last) line of a variable is expanded, so an overridden line cannot fail. A `${` takes any text up to the next `}` as the name, so `${a b}` is the variable named `a b` (unset: empty). The tests assert both edges (`tests/with-env/check.sh`: an entry of 131071 bytes runs and 131072 is refused; entries totalling 524287 run and 524288 are refused).
* A NUL byte in the file is a usage error naming its line (a NUL would end a name or value early in the C strings exec takes, so the rest of the line would be dropped or, after a newline, a variable injected); the file must be text.
* Corners, decided by what the comparable tools do and kept simple: a `# comment` after an unquoted value is part of the value (docker run --env-file: a `#` anywhere but the start of a line is part of the value, its documentation says; only a line that starts with `#` is a comment); an unbalanced quote (`A="x`) stays in the value as written; `\$` is not an escape, it is a backslash followed by an expansion; a `$` that starts neither `$NAME` nor `${NAME}` is a `$`; a line of another shape is passed over; CRLF line ends are accepted (the carriage return is not part of the value).
* The command line is read whole into 4096 bytes: argv[0] (bats's own name or path), `with-env`, the file, the command and its arguments, each with the NUL after it, must be at most 4095, else status 2.
* A command name with no `/` is looked for, as the shell does, in the directories of the PATH the command will run with: the file's `PATH` when it sets one (expanded as every value is), else bats's own; empty or unset is `/usr/bin:/bin` (as the process package's execvp does), an empty entry is the current directory. The first file that is not a directory and has an execute bit wins; a directory, or a file with no execute bit, is passed over, and when nothing better is found the status is 126 ("Permission denied"), not 127. The process package would look in bats's own PATH only (it calls `execvp` after the environment is fixed), so with-env finds the file itself (`file_exists_m`, `file_mode_m`, `dir_open_m`) and gives it the path, in an array of its own whose NUL is proved (`path_of_builder`, then `spawn_child_with`); a command with a `/` is run as named. An execute bit is any of the three, not whether this user may run it: a file only another user may run is chosen and fails with 126.
* Statuses: a usage error 2; a command found nowhere 127; one that cannot be run 126, with the system's reason (`strerror` through the process package's `os_error_text`: "Permission denied", "Exec format error").

**What with-env's types prove, and its silent defaults (a deviation from "never add runtime checks"):** In `src/with_env.bats` every read of the file's bytes (`read_byte`, `$A.read` with a proof `p < n`), every write into a name (`write_byte`), every use of the table with an index (`p < 6144`), every span (`[a,b,v:nat | a <= b; b <= n; ...]`, in `same_span` too: its bytes are read only where `a + j < ae <= n`, and it has no default for running out) and every entry number is proved by its types, from `line_assignment` on; the hash is `nmod`'d and bytes go through `$AR.low_byte`. What is not proved, said exactly:
* `table_read` clamps. The ints of the one-pass table (spans, chain links) are written as ints and read back as ints, and a value read from memory has no index in its type (the array package has no content-indexed int array: bats-lang/array#49), so it takes a value outside its bounds `[lo, m]` to be `lo`. It cannot happen (every value written is a position or entry number already in range). It is the only clamp of a value.
* `chain_find` stops, answering "not found", after 1100 steps (`fuel`). A chain of entries is linked by ints read from the table, and the types cannot say the chain ends (it does, since a link is always to an earlier entry, and there are at most 1024); the termination metric needs a bound, so the fuel is one. Without array#49 it stays.
* The builder writers of `src/helpers.bats` (`put_char_v`, `bput_v`, `copy_to_builder_v`) drop a byte that does not fit a full builder (524288 bytes) without a word. Every builder of this module stays far below that, by arithmetic in the code and not by the types: an entry over 131071 bytes is refused (status 2), never cut (the entry builder can briefly reach about 192 KiB (196607 bytes), 131071 of expansion plus up to 64 KiB of literal text, before that check), a name at 255, a value read at 65536, a command line at 4095, a path at about 130 KiB.
* `put_expanded` reads the byte after a `$` only when there is one (`p + 1 < n`) and takes none as "not a `{` and not a name", so a `$` at the end is a `$`; that is a branch in the code, not a default of a reader.
* `prerr_seg` (`put_seg` in `src/helpers.bats`) clamps silently: an index below 0 is read from 0, an index above the buffer's length prints nothing, and a length past the buffer's end stops at its end. It prints only with-env's error messages, which are diagnostics; no result of a command depends on it.
* Some end-of-buffer branches are unreachable and fall through silently, each excluded by the bound of the line that reaches it: `put_expanded` (`p + 2 > n`, which gives a literal `$`; `p + 1 < n` is checked first), `put_expanded` (`close + 1 > n`; `close < b <= n`), `table_fill` (`e + 1 > n`; `e <= size <= 65536 < n`), `arguments` (`z + 1 > 4096`) and `run_command` (`command_to + 1 > 4096`).
Everything else that was a clamp is gone: `byte_at`, `peek` and `poke_arr` of the helpers (which return 0 or ignore a position out of range) are no longer used here.

**What with-env cannot do yet, because of the process package (it owns the platform; bats adds neither `$UNSAFE` nor C):**

* **bats does not replace itself with the command, so a signal to bats does not reach it.** The script this replaced `exec`ed. Now `kill <bats>` (SIGTERM, SIGHUP) ends bats and leaves the command running, orphaned. with-env takes no project lock and no machine slot itself, but what the command starts (a `bats check` in it) does, and it keeps them until it ends. A terminal's Ctrl-C reaches both, since both are in the foreground process group. The process package has `spawn`, `child_wait`, `child_try_wait` and `child_pid`, and no `exec`, no `kill` and no signal handler; the env package has none either. The need is an `exec` that replaces the process (the platform's `execve`: Rust's `CommandExt::exec`, Python's `os.execve` and Go's `syscall.Exec` are the same call), which also removes the next limit. The need is filed as bats-lang/process#51; until it lands the limit stands, and `tests/with-env/check.sh` expects the orphan and fails when the signal does reach the command, so the change to exec is noticed.
* **A command a signal ended has status 1, not 128 + n.** The process package's `child_wait` returns the exit status when `WIFEXITED` and the same ~1 for a signal death, which cannot be told from a failure to wait, so a shell's convention (128 + the signal, which `sh`, Python's `subprocess` shell and `env` report) cannot be had; Rust's `ExitStatusExt::signal()` and Python's negative `returncode` are the platforms' way of keeping it. Filed as bats-lang/process#52 (what is needed: a `child_wait` outcome that says exited with a status or ended by a signal number). With `exec` the shell that started bats sees the real death and this limit goes away too.
