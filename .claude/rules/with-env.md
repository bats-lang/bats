# bats with-env

`bats with-env <env-file> <command> [args...]` (bats-lang/bats#277, a subcommand, the owner's ruling: bats has subcommands, not scripts) gives a shell that reads no profile (an agent's, a CI-like step) a machine's bats settings (`BATS_SLOTS`, `BATS_LOCK_DIR`, `BATS_CACHE_DIR`, `BATS_REPOSITORY`, and whatever else the machine sets, such as pwa's `PWA_TEST_SLOTS`): the file's variables are added to bats's environment (the file wins over the caller's) and the command is run with the arguments exactly as given and the standard streams shared; its exit status becomes bats's own. It is read as a dotenv file, not sourced by a shell (`src/with_env.bats`). It is read before bats's own arguments, so the command's own flags (`--help`, `--`) are its alone. Comparable tools: `env -S`, direnv, `dotenvx run` and `docker run --env-file` set the environment of one command from a file and run it; docker's and systemd's do not expand, dotenvx and Compose do. `tests/with-env` plays it.

Exact rules of the file and the command (all `tests/with-env/check.sh`):

* The file is at most 64 KiB (65536 bytes is read, 65537 is refused) and sets at most 1024 distinct variables. Which line is a variable's last is found in one pass over the file with a table of the names (a first version asked every line whether a later one overrode it: a 64 KiB file of comments took over a minute); the 1024 is because the process package's argument is an array of 512 KiB, so a variable costs about 130 KiB of memory and a tenth of a millisecond, and 7000 of them (all a 64 KiB file can name) took 1 GB and 3 seconds. 1024 is also far above any machine file's size: comparable tools set no count, so this is a bound bats needs and others do not.
* Corners, decided by what the comparable tools do and kept simple: a `# comment` after an unquoted value is part of the value (docker run --env-file: a `#` anywhere but the start of a line is part of the value, its documentation says; only a line that starts with `#` is a comment); an unbalanced quote (`A="x`) stays in the value as written; `\$` is not an escape, it is a backslash followed by an expansion; a `$` that starts neither `$NAME` nor `${NAME}` is a `$`; a line of another shape is passed over; CRLF line ends are accepted (the carriage return is not part of the value).
* The process package would look in bats's own PATH only (it calls `execvp` after the environment is fixed), so with-env finds the file itself.

**What with-env's types prove, and its silent defaults (a deviation from "never add runtime checks"):** In `src/with_env.bats` every read of the file's bytes (`read_byte`, `$A.read` with a proof `p < n`), every write into a name (`write_byte`), every cell of the table (an `iarr` of 2048 cells, read by `iarr_get_in` and written by `iarr_set_in` at an index proved below 2048), every span (`[a,b,v:nat | a <= b; b <= n; ...]`, in `same_span` too: its bytes are read only where `a + j < ae <= n`, and it has no default for running out) and every entry number is proved by its types, from `line_assignment` on; the hash is `nmod`'d and bytes go through `$AR.low_byte`. What is not proved, said exactly:
* The table finds, in one pass over the file, which line sets which variable. It is on array's `iarr` (bats-lang/array#49, bats-lang/bats#507; keyword: iarr table): `lines` (2048 cells, each within `[0, n]` by `ALLIN`: for the entry k counted from 0, cell 2k is where its line starts and cell 2k + 1 where it ends) and `links` (2048 cells within `[0, 1024]`: cell k, for the entry k counted from 0, holds the number, counted from 1, of the next entry of its bucket's chain, 0 being none; cell 1024 + h holds the number, counted from 1, of the latest entry whose name hashes to h, 0 being none). A line that sets a variable already in the table replaces that entry's line, so the time is that of the file and its chains, not of its lines squared. A file that sets more than 1024 variables is refused (the `table_put` that would add the 1025th answers 1025). The table is allocated zeroed (`allin_zeros`) and written only by `iarr_set_in`, so a cell comes back as `iarr_get_in` gives it, indexed by its bound, with no clamp (`table_read` is gone). An entry keeps its line, not its name's span: the name and the value are found again by `line_assignment`, whose result has `a <= b <= n` in its type, so no relation between two cells has to be stored (an `ALLIN` bound is uniform). Not proved: that a line stored in the table parses again as an assignment (it did when it was stored); `entries_make` and `chain_find` pass over an entry whose line does not, which cannot happen.
* `chain_find` stops, answering "not found", after `fuel` steps, and `fuel` is the number of entries the table holds (`table_put` passes its `count`, typed `<= 1024`, and `chain_find`'s fuel is typed `<= 1024`). A chain of entries is linked by ints read from the table, and the types cannot say the chain ends; it does, since a link is always to an earlier entry, so a chain has at most `count` entries and the fuel is never short. The termination metric needs a bound, so the fuel stays; it is tied to the entries, not to a constant.
* The builder writers of `src/helpers.bats` (`put_char_v`, `bput_v`, `copy_to_builder_v`) drop a byte that does not fit a full builder (524288 bytes) without a word. Every builder of this module stays far below that, by arithmetic in the code and not by the types: an entry over 131071 bytes is refused (status 2), never cut (the entry builder can briefly reach about 192 KiB (196607 bytes), 131071 of expansion plus up to 64 KiB of literal text, before that check), a name at 255, a value read at 65536, a command line at 4095, a path at about 130 KiB.
* `put_expanded` reads the byte after a `$` only when there is one (`p + 1 < n`) and takes none as "not a `{` and not a name", so a `$` at the end is a `$`; that is a branch in the code, not a default of a reader.
* `prerr_seg` (`put_seg` in `src/helpers.bats`) clamps silently: an index below 0 is read from 0, an index above the buffer's length prints nothing, and a length past the buffer's end stops at its end. It prints only with-env's error messages, which are diagnostics; no result of a command depends on it.
* Some end-of-buffer branches are unreachable and fall through silently, each excluded by the bound of the line that reaches it: `put_expanded` (`p + 2 > n`, which gives a literal `$`; `p + 1 < n` is checked first), `put_expanded` (`close + 1 > n`; `close < b <= n`), `table_fill` (`e + 1 > n`; `e <= size <= 65536 < n`), `arguments` (`z + 1 > 4096`) and `run_command` (`command_to + 1 > 4096`).
Everything else that was a clamp is gone: `byte_at`, `peek` and `poke_arr` of the helpers (which return 0 or ignore a position out of range) are no longer used here.

**What with-env cannot do yet, because of the process package (it owns the platform; bats adds neither `$UNSAFE` nor C):**

* **bats does not replace itself with the command, so a signal to bats does not reach it.** The script this replaced `exec`ed. Now `kill <bats>` (SIGTERM, SIGHUP) ends bats and leaves the command running, orphaned. with-env takes no project lock and no machine slot itself, but what the command starts (a `bats check` in it) does, and it keeps them until it ends. A terminal's Ctrl-C reaches both, since both are in the foreground process group. The process package has `spawn`, `child_wait`, `child_try_wait` and `child_pid`, and no `exec`, no `kill` and no signal handler; the env package has none either. The need is an `exec` that replaces the process (the platform's `execve`: Rust's `CommandExt::exec`, Python's `os.execve` and Go's `syscall.Exec` are the same call), which also removes the next limit. The need is filed as bats-lang/process#51; until it lands the limit stands, and `tests/with-env/check.sh` expects the orphan and fails when the signal does reach the command, so the change to exec is noticed.
* **A command a signal ended has status 1, not 128 + n.** The process package's `child_wait` returns the exit status when `WIFEXITED` and the same ~1 for a signal death, which cannot be told from a failure to wait, so a shell's convention (128 + the signal, which `sh`, Python's `subprocess` shell and `env` report) cannot be had; Rust's `ExitStatusExt::signal()` and Python's negative `returncode` are the platforms' way of keeping it. Filed as bats-lang/process#52 (what is needed: a `child_wait` outcome that says exited with a status or ended by a signal number). With `exec` the shell that started bats sees the real death and this limit goes away too.
