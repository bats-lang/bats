# bats check-pins (bats#390, repository-prototype#353)

`bats check-pins <file>...` fails on the inputs of CI that move under a passing commit. It replaces `scripts/check-pins.sh`, which read `uses:` lines alone (repository-prototype#352 found eight floating inputs it could not see). It is a subcommand written in bats (`src/pins.bats`, run before bats's own arguments are read, as `with-env` is), per quire#646: we write bats, not shell. The shell expands the files (`.github/workflows/*.yml .github/actions/*/action.yml`) for the arguments, so bats lists no directory for those; `bats check-pins --discover` (bats#391, the only argument) asks git for them itself: `git ls-files -z --cached --others --exclude-standard` over `.github/workflows/*.yml` and `.yaml`, `.github/actions/*/action.yml` and `.yaml`, `**/package.json` and `**/ats2.bats` (git's glob pathspecs), run through the process package from the current directory, so tracked files and untracked ones that are not ignored are checked and `bats_modules/` and `build/` are not. Name, by research: pinact's `run` and zizmor discover the workflows themselves when none is named; `--discover` is the mode that does it here and no argument stays the usage (status 2), which the setup action's probe relies on. A failed git, a list that fills the 4096 bytes (it is read into the buffer the arguments are, so it is the same limit) and an empty list are status 2. Each failure is `file:line: ...` on stderr, the status is 1 for a failure, 2 for no file or an unreadable one; a clean run prints nothing.

Name, by research: `check-pins` follows the script it replaces and the repository's verb-noun subcommands (`clone-repository`, `record-commit`); `bats check` is the type-check. Comparable tools: pinact (`run --check`), ratchet (`check`) and zizmor's unpinned-uses audit name the thing checked and read `uses:` only.

## The rules (a workflow or action, by file name anything else than `package.json` and `ats2.bats`)

* `uses:` is `./...` or `owner/repo[/path]@<40 lowercase hex>` followed by a comment that has text (the version).
* `runs-on`, `os` (a matrix's) and the items of their lists: no label ending in `-latest` (a longer name such as `ubuntu-latest-x` is not one).
* `node-version`, `java-version`, `python-version`: three numbers and then nothing or a `-` or `+` suffix (`22.23.3`, `21.0.12+8.0.LTS`, `1.2.3-rc.1`), quoted or not; a `${{ ... }}` expression is accepted (its source is checked where the literal is); a `*-version-file` is another key, accepted. A key with no value on its line (an action input) is checked at the `default:` under it.
* A command (in the position of one: first word after `- `, `run:`, `&&`, `||`, `|`, `;`, `(`, `sudo`, `then`, `do`, `else`, `exec`), so `echo "npm install"`, a comment and a `name:` are not commands: `npm install` or `npm i` (use `npm ci`); `pnpm install` or `pnpm i` with no `--frozen-lockfile` on the line; `npx` whose first non-flag word is not `name@<exact version>`; `curl` or `wget` when no line of the step (the list item that holds the line, to the next line indented as little) holds `sha256sum`, `shasum`, `sha512sum`, `sha384sum` or `b2sum`. `apt-get install` is allowed (the runner image is pinned).
* A `package.json` (by its name): each entry of `dependencies`, `devDependencies` and `optionalDependencies` is `"name": "version"` on a line of its own with an exact version `github:owner/repo#<40 hex>` or `workspace:...` (a pnpm workspace package: local source, pinned by the commit itself, not fetched from a registry); a lock (`package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`) is beside it when it has any entry. A member of a pnpm workspace has its lock at the workspace root (bats#484, keyword: pnpm workspace lock): the nearest directory at or above the `package.json` that holds a `pnpm-workspace.yaml` also holds a `pnpm-lock.yaml`. Only the existence of the two files is tested and neither is read. `peerDependencies` are the package's API, not an install, and are not read. It is read by lines, not parsed (the json package would add a dependency to the compiler): a section whose entries are not one to a line is refused, never passed.
* `src/ats2.bats`, named among the files: `#define ATS2_SHA256 "<64 lowercase hex>"` and `#define ATS2_URL "https://...tgz"` are there, and then no workflow or action named beside it holds `ATS2-Postiats` or a run of 64 hex digits outside a `uses:` line (the script's rule: the ATS2 pin is in `src/ats2.bats` alone, bats#283).

## Exceptions

`# unpinned: <reason>` on the line of an input, or above it (on a comment line, with only comment lines between), is accepted and listed on stdout (`file:line: unpinned: <reason>`), so each is a decision somebody wrote. An exception with no reason, or one that exempts nothing (a stale decision: a blank line, a code line that is clean, or the end of the file after it), is a failure, as linters that report unused suppressions do (ESLint's `--report-unused-disable-directives`). A `package.json` has no comments, so its exception is a marker file in the directory (below, keyword: check-pins-fixture).

## What is proved, tested and limited

Every read of the file's bytes is proved in range by the types (`src/pins.bats` is the style of `with_env.bats`: `read_byte` with `p < n`, spans indexed, every loop with a metric); no position is moved into range: `byte_in` answers 0 at and past a span's end, a value for a read beyond the span, never a read. Tested (`tests/check-pins/check.sh`): accept and reject fixtures for every rule, the near misses (a label inside a longer name, an exact version that looks like a range, a command word inside `echo`, a command in a comment or a `name:`), the exceptions, many lines, a last line with no newline, and this repository's own files. Limits, said exactly: the command line is read into 4096 bytes, so a run whose arguments total 4095 bytes or more is refused with status 2 (the shell expands the files, so a very long list reaches it); a line is a line (a value that continues on the next is not joined); `pnpm install` takes its flag from the same line; a command after `$(` or a backtick is not in command position; a step is found by indentation (a list item), so a `curl` outside any list item takes the whole file as its step; a version key that is a list on following lines is not read.

## A pnpm workspace's lock (bats#484, keyword: pnpm workspace lock)

Decision: a `package.json` with dependencies has its lock when a lock is beside it, or when the nearest directory at or above it that holds a `pnpm-workspace.yaml` also holds a `pnpm-lock.yaml`; the walk goes up one directory at a time through the path as named (the empty directory at the top of a relative path is the current directory), stops at the first `pnpm-workspace.yaml` (an inner workspace is its own root, so the outer lock does not cover it), at the filesystem root, and at a `..` component (the path does not say what is above it). No file is read or parsed: only whether the two files exist, so `pnpm-workspace.yaml` is never matched by pattern (YAML is not read in this compiler, quire#646).

Research: pnpm defines a workspace by a `pnpm-workspace.yaml` at its root (pnpm docs, "Workspace") and, with `shared-workspace-lockfile` true (the default; pnpm docs, "Settings"), keeps one `pnpm-lock.yaml` for all members, at that root, with an importer for each; a lock beside each member would contradict the repository that has the workspace. pnpm itself finds the root by looking for `pnpm-workspace.yaml` in the current directory and then each parent, nearest first, which is the walk here. npm (the `workspaces` field of the root `package.json`, one `package-lock.json` at the root), yarn and bun (the same field, `yarn.lock` and `bun.lock` at the root) name their members inside a `package.json`, not in a file whose existence says it: deciding them needs the root's `package.json` read for that field, which this by-lines reader does not do, so a member of those workspaces still needs a lock beside it. `--discover` and the caller's file names are relative to the repository root (the audit runs it there), so the walk reaches the workspace root; a `..` path below a workspace root is not walked past.

Tested (`tests/check-pins/check.sh`, `workspace-*`): a member two levels below the root with the lock at the root is accepted by absolute and by relative paths; the same tree without `pnpm-lock.yaml` is refused with the no-lock message at line 1; a nested workspace without its own lock is refused under an outer lock and accepted with its own; a `pnpm-lock.yaml` above with no `pnpm-workspace.yaml` is refused; `--discover` from the root accepts the members and refuses them when the lock is removed. Proved: the walk's reads of the path are in range by the types (`component_start` and `parent_dir` index below 4096 and `workspace_lock` has the metric `e - a`).


## A directory of test fixtures: `check-pins-fixture` (bats#504, keyword: check-pins-fixture)

Rule: a file named `check-pins-fixture` in a directory exempts every `package.json` at or below that directory from the exact-version and lock rules, and its first line is the reason (text after blanks are trimmed). Each exempted file is printed on stdout as `<package.json>:1: unpinned: <reason>`, as a workflow exception is. Two failures, as an unused `# unpinned:` is one: a marker whose first line has no text (the package.json files under it are then checked as if it were absent), and a marker with no `package.json` at or below it among the files checked (a stale decision; `--discover` lists markers and package.json files alike, with explicit arguments the marker and the package.json files are named together, as `src/ats2.bats` is). The marker is found by its existence, walking up from the `package.json` one directory at a time exactly as the pnpm workspace lock does (`parent_dir`; the nearest marker decides; the walk stops at the top of the path, the filesystem root and a `..` component), so an inner marker covers its own subtree and a sibling directory or the directory above it is not covered. "At or below" for the stale check is the same walk (`reaches_dir`), not a textual prefix. No YAML or JSON is read, and only the first line of the marker is read, from a whole-file read bounded by the types like the others.

Why a file: a fixture's ranges are the point of the fixture (a relock test moves a dependency inside its range), so they cannot be made exact; weakening the rule for every `package.json`, or listing paths in an allowlist, would hide real floating inputs. A marker travels with the directory it exempts, the reason is a line a reviewer reads in the diff that adds it, and the checker reads existence and bytes only (quire#646).

Research (how comparable tools declare a directory of fixtures):

* ESLint: file ignores are `ignorePatterns`/`ignores` patterns in a config, and a disable comment takes a description after `--` ("must come after the configuration", docs "Configure Rules"); `--report-unused-disable-directives` reports a directive that suppresses nothing, which is the model for the empty and stale cases here. Its path patterns live in a config far from the directory, which is what a marker avoids.
* Dependabot: `ignore` filters dependencies by name, version or update type, and `directories` (globs) says where manifests are looked for (docs "Dependabot options reference"); neither is a per-directory declaration with a reason, and neither reports a stale entry.
* Renovate: `ignorePaths` globs in the config; the `:ignoreModulesAndTests` preset ignores `**/test/**`, `**/tests/**`, `**/__fixtures__/**`, `**/examples/**` and similar by directory name, so a tool skips fixtures by convention. A name convention here would exempt a real `tests/` package and gives no reason, so it is not used.
* zizmor: `rules.<id>.ignore` entries `file[:line[:col]]` in `zizmor.yml`, and `# zizmor: ignore[rule]` inline with an optional trailing explanation; it does not document a report of unused ignores. pinact: `.pinact.yaml` with `files[].pattern` and `ignore_actions` (name and ref regexes), whose own docs steer new configurations to `rules` with `ignore`. All are a central list, and the entry carries no reason.
* npm: `.npmignore` is read in every subdirectory of a package, like `.gitignore` (docs "Developers"), so a file whose existence changes the rules for its directory and below is established practice; its content is patterns, where a marker's content is a reason.

Tested (`tests/check-pins/check.sh`, `fixture-marker-*`): a range below a marker, two levels down, by absolute and by relative paths, is accepted and listed; the same tree without the marker is refused with the range message; markers with no reason (empty, blanks, a blank first line) are refused and exempt nothing; a marker with no `package.json` at or below it is refused, and neither a sibling nor a sibling of the same prefix or length counts as below; an inner marker covers its own subtree only (its sibling and the directory above stay refused); `--discover` lists markers and accepts, refuses without the marker, and refuses a stale one. Each class was shown to fail by mutating `src/pins.bats` (the marker name, the reason test, the stale test, the walk, the directory comparison). Proved: the walk and the comparison index below 4096 by their types (`same_range` has the metric `len`, `reaches_dir` and `marker_dir` `e - a`), the reason is read inside the file by `line_end`, `skip_blank` and `trim_end`.
