# The shared cache (BATS_CACHE_DIR)

patsopt's C names the project's files relative to the project (`build/src/m.dats`): after patsopt succeeds, `src/cache.bats` takes the project's directory out of the paths it wrote, plain in comments and mangled into symbol names, where it is followed by `build/` (`build_057_`), as GCC's `-ffile-prefix-map` or Rust's `--remap-path-prefix` do. The same sources give the same C at any path, so a `build/` and the shared cache below are valid wherever the checkout is; ATS's `$mylocation` names its file relative to the project. The Rust bats's C held the absolute path, so a `build/` was valid only where it was made. patsopt writes `<C>.raw`, which is rewritten beside the C and renamed into place, so a bats stopped at any point never leaves a C that is half written or still holds the path (`tests/project-lock`, `tests/shared-cache`).

With `BATS_CACHE_DIR` set, patsopt's C is kept there, under a key of what patsopt reads: the toolchain (a listing of `$PATSHOME/bin/patsopt` and the files of `prelude/`, `libats/`, `share/`, `ccomp/` by their sha256, made once per process; `sha256sum`, or `shasum -a 256` where it is absent, bats-lang/bats#318: `cksum`'s 32 bits missed a same-size change), patsopt's arguments, and the module's `.dats` with every file its staloads and includes reach (`patsopt --depgen`, followed to the end), each by path and sha256. A module bats would run patsopt on is looked up first; a hit is copied into place and checked as patsopt's output is (template instances, capturing lambdas), and only a run that passed those checks is kept, so a hit never passes what a cold build fails. Entries are written beside their place and renamed into it, so checkouts share the cache with no lock; one unused for 7 days is removed (at most once a day, after a store), and the cache is bounded in size too (below). The Rust bats had no cache shared between checkouts (`tests/shared-cache`).

Neither an object nor a key of an object is kept here: the shared cache holds patsopt's C, which
names the project's files relative to the project, and the shared cache's key lists names under
`build/`; an object's key is in build-freshness.md.

## Size bound (bats#483)

An age limit alone bounds nothing useful at the churn of a busy machine (a module revision is an entry that only its exact toolchain and sources ever hit again; on 2026-10-23 the cache held 8,673 files, 5.3 GB). `BATS_CACHE_MAX_MB` is the limit in whole megabytes of entries' C (default 2048); a value that is not a whole number is said on stderr (`warning: BATS_CACHE_MAX_MB='x' is not a whole number of megabytes; 2048 is used`) and the default is used. At the first store of a process, when the entries hold more than the limit, the least recently used are removed until they hold at most 90% of it (the headroom is what keeps every store of the next builds from pruning again). One scan a process: a build may exceed the limit by what it stores after that scan, and the next process prunes it.

**Recency** is the entry file's modification time: a store sets it, and a hit touches the entry (`touch` in `run_patsopt`). It orders removal only and is never read to decide that a C is usable: a hit is judged by its key, the content hashes of everything patsopt read, and is checked as patsopt's output is, so a stale entry can never be served by being recent, and a removed one is only a miss. Where the mtimes tie (one second), either may go first.

**A removal never breaks a concurrent build.** Entries are written beside their place and renamed, a hit is copied beside the C and renamed (`cp` then `mv`, after `[ -f ]`), so a reader whose entry was removed between the test and the copy gets a failed `cp`, counts it as a miss and runs patsopt cold; it never reads half an entry. `rm -f` of an entry another process already removed is not an error.

**What comparable caches do.** ccache's `max_size` (default 5 GiB, "approximate LRU order based on the modification time of files in the cache", hits update the mtime, cleanup is triggered after a store when the limit is exceeded; https://ccache.dev/manual/latest.html). sccache's `SCCACHE_CACHE_SIZE` (default 10G for the disk cache; https://github.com/mozilla/sccache/blob/main/docs/Configuration.md). Bazel's disk cache has `--experimental_disk_cache_gc_max_size` and `--experimental_disk_cache_gc_max_age` (since 7.4; collects while idle between builds, https://bazel.build/remote/caching). All three bound by size, as an environment or flag setting with a default, and ccache says it orders entries by recency of use (mtime). bats follows ccache's trigger (after a store) and order (mtime, touched by a hit). The default is 2048 MB, below those (5 and 10 GiB) because the cache here shares a disk allowance with checkouts and each CI run restores it: this machine's 5.3 GB cache filled a 99% full disk. The scan is `stat` over the entries (GNU `stat -c`, else BSD `stat -f`), sorted by mtime, so it needs no `ls` argument list and no `find -printf`.

`tests/shared-cache` fills a cache past `BATS_CACHE_MAX_MB=1` with entries of known ages beside entries a build has just hit, then a store: the oldest are gone, the newest filler and everything the build used remain, the entries hold at most the limit, a build against the pruned cache gives the C of a cold build, and a limit that is no number is said.
